# 기능 명세: CudaAsync와 원본 영상 사용 종료

**기능**: `014-async-step` · **갱신일**: 2026-10-09 · **상태**: 명세 완료

최신 사용자 요청은 CudaAsync의 보호 복사를 없애고 YOLO·TensorRT의 RGB 전처리 후 원본 영상 사용 종료를 알리는 것이다. 기존 이름 변경·복수 단계·핫스왑·스트림 관리 요구사항은 유지한다.

## 사용자 시나리오

### 영상 전달의 대기 제한 (우선순위 1)

정상 완료한 결과를 같은 원본 컨텍스트에 적용한다. RGB 전처리 후 원본 사용 완료가 확인된 요청이 타임아웃되면 원본을 그대로 전달한다. 사용 완료가 확인되지 않으면 해당 프레임만 폐기하며 기다리거나 복사하지 않는다. 작업자가 바쁘면 다른 입력은 제출하지 않고 그대로 전달한다. 늦은 결과는 적용하지 않는다.

검증은 완료·미완료 이벤트, 차단된 작업, 원본 텐서 동일성과 다음 입력 진행을 확인한다.

### RGB 전처리와 원본 독립 (우선순위 1)

YOLO 개별·배치와 TensorRT 전처리는 별도 RGB 텐서를 생성하고 원본 읽기의 CUDA 완료 이벤트로 사용 종료를 알린다. 이후 추론·후처리는 원본을 읽지 않는다. 바깥 BoxOverlay가 원본을 수정해도 독립 RGB와 추론 결과에 영향을 주지 않는다.

### 상태와 자원 유지 (우선순위 2)

처리 반복자·핫스왑·클래스별 YAML 구성·중앙 직렬화·모델 스트림을 유지한다. 폐기된 입력도 작업 완료까지 참조를 보관한다. 정상·실패·조기 종료·재사용을 검증한다.

## 기능 요구사항

- FR-001: 일반 Step을 감싼 CudaAsync를 선택적으로 등록한다.
- FR-002: timeout_ms 기본값은 5이며 유한한 0 이상의 숫자만 허용한다.
- FR-003: 정상 결과를 같은 원본 컨텍스트에 적용하고 전달되는 입력의 순서를 유지한다.
- FR-004: 시간 초과 시 사용 완료가 확인된 입력만 전달하고 나머지는 폐기한다. 제시간에 정리된 오류에는 원본을 전달한다.
- FR-005: 인스턴스당 진행 중 요청은 하나이며 바쁠 때 새 입력은 제출하지 않는다. 늦은 결과는 폐기한다.
- FR-006: 작업 반복자와 요청별 실행 문맥을 유지한다.
- FR-007: 모든 CudaAsync 경로에서 입력 텐서·중첩 데이터를 복제하거나 깊은 복사하지 않는다. 작업 속성 사전만 분리하고 공유 데이터는 읽기 전용이다.
- FR-008: 입력 종료 시 새 요청을 중단하고 호출자를 무한 대기시키지 않는다. 남은 작업자가 자원을 정리한다.
- FR-009: 내부 Step은 입력 하나당 출력 하나 계약을 지킨다. 정리된 계약 오류는 로그와 원본 전달로 처리한다.
- FR-010: 공개 가져오기·현재 정책 안내·자동 검증을 제공한다.
- FR-011: 과거 async 및 async_step 이름 변경은 최신 FR-024로 대체한다.
- FR-012: CUDA 입력 준비와 작업 종료를 확인하고 원본 참조를 완료까지 유지한다. 영상·감지 결과를 CPU로 복사하지 않는다.
- FR-013: 기존 release_input은 모든 공유 입력 사용 종료 계약으로 단일 Step에서만 적용한다. 신호 없음·미완료·조회 실패에는 복사 대신 프레임을 폐기한다.
- FR-014: 요청 전체에 하나의 기한을 적용한다. 만료 후 미시작 Step은 건너뛰고 실행 중 함수·GPU 작업은 강제로 중단하지 않는다.
- FR-015: 복수 Step에서 전체 입력 release_input은 무시하지만 원본 영상 release_frame은 적용한다. 신호 후 내부 후속 Step은 원본을 다시 사용하지 않는다.
- FR-016: 내부 설정은 FR-020~021을 따른다. 예전 step·steps 구성 매핑은 지원하지 않는다.
- FR-017: 중앙 전달은 복수·중첩 CudaAsync와 Tap·Hotswap의 모든 사용자 모듈을 값으로 직렬화한다.
- FR-018: 내부 사용자 Step은 처리 경계에서 코드를 핫스왑하고 상태·최신 설정을 유지한다. 잘못된 코드에서는 기존 구현을 유지한다.
- FR-019: 실행 중 Step은 교체하지 않으며 오류는 공통 정책으로 처리한다.
- FR-020: CudaAsync.configure는 timeout_ms만 받고 다른 키는 오류로 거부한다.
- FR-021: 사용자·내장·명시적 Hotswap·중첩 단계 설정을 클래스명 최상위 YAML 섹션에서 독립 적용한다.
- FR-022: CudaAsync(*steps, timeout_ms=5)는 하나 이상의 Step을 순서대로 실행하고 steps 튜플 및 첫 단계의 step 속성을 제공한다.
- FR-024: 공개 이름은 CudaAsync이며 구현 모듈은 cuda_async.py이다.
- FR-025: 장치별 모델 CUDA 스트림을 생성·재사용하고 input.cuda_stream은 영상용으로 유지한다.
- FR-026: 내부 YOLO·TensorRT 전후처리·추론은 모델 스트림을 사용하며 단독 실행과 공유 배치 스트림은 유지한다.
- FR-027~028: 이전 타임아웃 복사와 실패 정책은 FR-007·FR-029로 대체한다. 복사 스트림·보관 목록·정리 스레드를 제거한다.
- FR-029: 요청별 release_frame(ready_event=...)을 제공한다. 이벤트 query 완료 또는 요청 전체 GPU 정리 완료 시에만 타임아웃 원본을 전달한다. 사용 중이면 추가 대기 없이 폐기한다.
- FR-030: YOLO 개별·배치와 예제 TensorRTPreProcess는 별도 RGB 생성 직후 이벤트를 기록해 release_frame을 호출한다. YOLO 제출 전 NV12 보호 복제를 RGB 생성으로 대체하고 local_yolo의 기존 NV12 직접 호출을 유지한다.
- FR-031: 영상 신호는 요청 문맥에 귀속되며 오래된 콜백이 다른 요청을 해제하지 못한다. 원본 참조는 실행 중 GPU 작업 종료까지 유지한다.

## 성공 기준

- SC-001: 정상 결과·동일 객체·전달 순서가 유지된다.
- SC-002: 작업자 차단 중 후속 100개 입력이 진행되며 요청이 쌓이지 않는다.
- SC-003: 차단 요청의 타임아웃 처리와 호출자 종료는 자동 검증에서 각각 0.5초 이내다. 운영 환경의 절대 시간 보장은 하지 않는다.
- SC-004: 복수 단계·후속 생략·오류 복구·상태·정리·설정·직렬화 회귀가 통과한다.
- SC-005~007: 중앙 전달·코드 핫스왑·독립 YAML 적용 회귀가 통과한다.
- SC-008~009: 공개 이름과 모델 스트림 회귀가 통과한다.
- SC-010: 이전 GPU 복사 검증은 SC-011로 대체한다.
- SC-011: 입력 복제 없이 미완료 이벤트에서는 폐기하고 완료 이벤트에서는 원본 동일성·늦은 결과 격리를 확인한다. 복수 영상 신호·요청별 격리를 검증한다.
- SC-012: 실제 CUDA에서 YOLO 개별·배치 및 TensorRT 전처리의 독립 RGB·종료 이벤트·원본 수정 안전성을 확인하고 기존 추론 회귀가 통과한다.

## 명확화와 경계 조건

2026-10-09: RTG 전처리는 문맥상 RGB 전처리를 뜻한다. 원본 영상 사용 종료 계약은 앞선 대화에서 확정됐다. 이벤트 미완료 시 원본을 안전하게 전달할 수 없으므로 해당 프레임을 폐기한다. 추가 질문은 필요하지 않다.

신호 후 같은 CudaAsync의 후속 Step은 원본을 다시 읽거나 수정하지 않는다. 원본을 그리는 BoxOverlay는 바깥에 둔다. 다른 공유 입력도 읽기 전용이다. 신호 없는 일반 Step도 사용할 수 있지만 실행 중 타임아웃 입력은 폐기된다. 0ms는 결과를 기다리지 않는다. 소스·다중 입력 집계·다중 출력은 지원하지 않는다. CUDA 런타임 호출 자체의 지연 및 외부 부작용 취소는 보장하지 않는다.
