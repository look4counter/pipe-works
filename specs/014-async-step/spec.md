# 기능 명세: 선택적 비동기 단계

**기능**: `014-async-step` · **작성일**: 2026-10-09 · **상태**: 명세 완료

**사용자 요청**: `pipeworks/embedded/async_step.py`에 일반 처리 단계를 감싸는 `Async`를 추가한다. 이번에는 모델 단계의 변경이나 배치 옵션 추가를 포함하지 않는다.

## 사용자 시나리오와 검증

### 사용자 이야기 1 — 영상 전달의 대기 제한 (P1)

사용자는 처리 단계를 비동기로 실행하고 지연이나 오류가 발생하면 원본 입력을 전달한다.

**독립 검증**: 성공, 지연, 예외를 발생시키는 일반 처리 단계로 결과와 전달 순서를 확인한다.

**수용 시나리오**:

1. 결과가 제한 시간 안에 나오면 원본 컨텍스트에 처리 결과를 반영하고 같은 원본 객체를 전달한다.
2. 작업이 지연되거나 실패하면 원본 속성과 데이터가 그대로 전달된다.
3. 이전 요청이 진행 중이면 후속 입력을 대기 없이 전달하고 작업을 누적하지 않는다.
4. 늦은 결과는 원본이나 후속 입력에 반영하지 않는다.

### 사용자 이야기 2 — 상태와 자원 유지 (P2)

사용자는 프레임 간 상태를 유지하는 단계도 감싸고, 종료 시 영상을 오래 기다리지 않는다.

**독립 검증**: 연속 번호를 기록하는 단계, 중첩 가변 데이터, GPU 입력, 작업을 막는 단계로 검증한다.

**수용 시나리오**:

1. 정상 처리 동안 감싼 단계의 입력 스트림을 유지하여 지역 상태가 초기화되지 않는다.
2. 작업용 컨텍스트의 속성 변경은 성공한 요청에만 반영된다. 공유 텐서와 중첩 데이터는 읽기 전용이다.
3. 입력 종료 또는 조기 종료 시 실행 중인 작업을 무한히 기다리지 않는다. 작업이 끝나면 자원을 정리한다.

### 경계 조건

- 제한 시간 0은 기다리지 않는 실행을 뜻한다. 음수, 무한대, 불리언, 문자열은 거부한다.
- 입력보다 출력을 먼저 내거나, 출력 전에 두 번째 입력을 요구하거나, 입력을 처리하지 않고 끝나는 단계는 계약 위반으로 로그를 남기고 해당 입력을 통과시킨다.
- 처리 예외 후 다음 요청은 새 처리 스트림으로 재시도한다. 외부 저장이나 전송 부작용은 되돌리지 않는다.
- 정상 완료 시 복사할 수 없는 입력도 사용할 수 있다. 타임아웃 복사 실패 시 실행 중인 작업의 완료를 기다려 안전하게 원본을 전달한다. 이 예외 경로는 대기 제한을 넘을 수 있다.

## 요구사항

### 기능 요구사항

- **FR-001**: 사용자는 일반 처리 단계를 감싼 `Async`를 선택적으로 등록할 수 있어야 한다.
- **FR-002**: 제한 시간의 기본값은 5ms이며 생성자와 구성에서 유한한 0 이상의 값을 지정할 수 있어야 한다.
- **FR-003**: 성공 결과를 같은 원본 컨텍스트에 반영하고 입력 순서를 유지해야 한다.
- **FR-004**: 시간 초과에는 복사한 입력 데이터를 같은 원본 컨텍스트에 반영해 전달한다. 제시간에 끝난 처리 실패에는 원본을 전달한다. 복사 실패는 로그를 남기고 실행 중 작업 완료 후 원본을 전달한다.
- **FR-005**: 진행 중 요청은 하나로 제한하고 늦은 결과는 폐기해야 한다.
- **FR-006**: 정상 처리 스트림과 작업 스레드의 실행 문맥을 유지해야 한다.
- **FR-007**: 정상 완료와 사용 중 통과에는 입력 데이터를 복사하지 않는다. 작업용 컨텍스트의 속성 사전만 분리하고 공유 데이터는 읽기 전용으로 사용한다. 타임아웃에만 후속 전달용 중첩 데이터·텐서·DLPack 프레임을 복사하고, 복사 완료를 확인한 뒤 전달한다. 실행 중 작업에는 원본 입력 소유권을 완료까지 유지한다.
- **FR-012**: CUDA 입력의 준비와 작업 완료를 확인하고 늦은 작업에서 원본 수명을 유지해야 한다. GPU 복사는 GPU 안에서만 수행하며 CPU로 영상이나 감지 결과를 전송하지 않는다.
- **FR-013**: 입력 사용 종료 신호는 선택 사항이다. 해당 요청에서 신호와 선택적 CUDA 이벤트 완료를 확인하면 타임아웃 복사를 생략한다. 신호가 없거나 이벤트 미완료·조회 실패면 기존 복사를 유지한다. 신호는 요청 실행 문맥에서 격리하고 Async 밖에서는 아무 동작도 하지 않는다.
- **FR-008**: 종료 시 새 요청을 중단하고 무한 대기 없이 작업 스트림을 정리해야 한다.
- **FR-009**: 한 입력당 한 출력을 내는 단계의 계약을 검증하고 위반 시 원본을 통과시켜야 한다.
- **FR-010**: 공개 가져오기, 설정 전달, 사용 안내와 자동 검증을 제공해야 한다. 모델 단계의 기존 동작은 변경하지 않는다.
- **FR-011**: 2026-10-09 후속 요청에 따라 모듈 파일명을 `async_step.py`로 바꾸고 직접 가져오기와 기존 패키지 공개 가져오기를 모두 지원해야 한다. 클래스 이름과 실행 동작은 유지한다.

### 주요 개체

- 원본 입력: 영상 파이프라인에 전달할 컨텍스트.
- 작업 요청: 분리된 입력, 실행 문맥, 완료 신호, 기한과 결과를 가진 단위.
- 비동기 단계: 하나의 감싼 단계와 제한 시간을 갖는 실행 정책.

## 성공 기준

- **SC-001**: 성공, 실패, 지연, 사용 중 통과 시나리오에서 입력 순서와 원본 객체 식별을 100% 유지한다.
- **SC-002**: 차단된 작업에서 100개 후속 입력을 처리해도 요청 수는 하나이며, 원본 데이터에 늦은 수정이 발생하지 않는다.
- **SC-003**: 차단 작업을 포함한 자동 검증에서 제한 시간 10ms 요청의 전달과 종료는 각각 0.5초 안에 끝난다. 일반 운영 환경에서 실시간 보장은 하지 않는다.

## 가정과 범위

- `Async`는 소스, 다중 입력 집계, 다중 출력 단계에 적용하지 않는다.
- 전달을 건너뛴 입력은 내부 처리 단계가 보지 않으므로 내부 간격 카운터는 실제 제출된 입력만 센다.
- 제한 시간은 입력 준비와 작업 완료 대기에 적용한다. 타임아웃 후 복사 완료만큼 전달이 늦어질 수 있으며 복사를 강제 중단하지 않는다.
- 감싼 Step은 공유 입력을 제자리에서 수정하지 않고, 결과를 새 속성이나 새 데이터로 반환해야 한다. 공유 입력의 변경 롤백과 외부 부작용 취소는 지원하지 않는다.
- 모델 내부 비동기 처리를 제거하거나 `batch` 옵션을 추가하는 일은 후속 작업이다.

## 복수 Step 후속 계약

- **FR-013**: Async(*steps, timeout_ms=5)는 하나 이상의 Step을 순서대로 처리하며 전체 요청에 단일 제한 시간을 적용한다. 기존 단일 Step API와 step 속성은 보존하고 steps 튜플로 전체 목록을 제공한다.
- **FR-014**: 제한 시간 초과 후 아직 시작하지 않은 Step은 건너뛰며 실행 중인 함수·GPU 작업은 강제 중단하지 않는다. 늦은 결과는 버리고 원본 전달·입력 보호·사용 중 통과를 유지한다. 각 Step은 입력당 한 출력 계약을 지킨다.
- **FR-015**: 복수 모드는 중간 입력 사용 종료 신호를 무시하여 전체 입력 보호를 유지한다. 단일 모드의 신호 최적화는 유지한다. 처리 반복자·상태와 종료·오류 복구·직렬화를 보존한다.
- **FR-016**: 단일 모드의 step 매핑과 평면 설정을 유지한다. 복수 모드는 steps 목록으로 각 Step의 설정 매핑을 순서대로 받으며 생략 시 빈 설정을 전달한다. 잘못된 길이·매핑과 단일용 설정은 오류로 처리한다.
- **SC-004**: 복수 단계의 순서·중간 결과·상태 유지·전체 타임아웃·남은 작업 생략·입력 보호·오류 복구·정리·설정·직렬화 검증이 통과한다.

명확화: 사용자는 배열 대신 개수 제한 없는 위치 인자를 요청했다. 빈 목록은 허용하지 않으며 timeout_ms는 키워드 인자다. 취소는 남은 단계 생략이며 실행 중인 작업의 강제 중단은 포함하지 않는다. 복수 모드에서는 입력 사용 종료 신호 최적화를 보수적으로 끈다. 추가 질문이 필요한 모호성은 없다.
## 중앙 전달 회귀 수정

- **FR-017**: 중앙 전달은 복수 Async 내부의 모든 사용자 Step 모듈을 값으로 직렬화하도록 등록한다. 중첩 Async·Tap·Hotswap도 탐색하며 예제 전용 모듈이 중앙 프로세스 경로에 없어도 역직렬화할 수 있어야 한다.
- **SC-005**: 서로 다른 임시 모듈의 복수 Step을 감싼 파이프라인을 전달하고 모듈이 없는 환경에서 역직렬화할 수 있다.

명확화: 보고된 ModuleNotFoundError는 복수 Async의 첫 Step만 등록하는 누락이다. 모듈 검색 경로 확장 대신 기존 값 직렬화 정책을 모든 내부 Step으로 확장한다. 사용자 예제 변경은 보존한다. 추가 질문은 필요하지 않다.
## 내부 코드 핫스왑

- **FR-018**: 단일·복수 Async 내부 사용자 Step은 처리 경계에서 코드 변경을 감시하고 유효한 구현으로 교체한다. 기존 Hotswap과 내장 Step은 중복 감싸지 않는다. 상태와 최신 설정을 재적용하고 잘못된 코드에서는 기존 구현을 유지한다.
- **FR-019**: 실행 중인 Step은 교체하지 않고 이후 입력에서 변경을 적용한다. 오류 원본 전달·타임아웃·신호 보호·종료·중앙 직렬화 계약을 유지한다.
- **SC-006**: 단일·복수 사용자 파일 변경, 잘못된 코드와 복구, 최신 설정 재적용 및 기존 Async·Hotswap·중앙 전달 회귀가 통과한다.

명확화: 기존 자동 핫스왑 제외 결정을 최신 요청으로 대체한다. 감시 간격과 상태 이전은 기존 Hotswap 정책을 재사용한다. Async의 원본 전달 정책을 위해 내부 자동 래퍼는 오류를 Async로 전파한다. 추가 질문은 필요하지 않다.
## 내부 설정 독립 전달

- **FR-020**: Async.configure는 timeout_ms만 처리한다. step·steps·평면 내부 설정 전달은 제거하고 지원하지 않는 키는 안내 오류로 거부한다. 내부 Step의 초기 설정은 파이프라인이 해당 클래스명 최상위 YAML 섹션으로 전달한다.
- **FR-021**: 내부 사용자·내장·명시적 Hotswap 및 중첩 Async의 YAML 변경을 각 처리 경계에서 독립 적용한다. 한 단계의 설정 오류는 해당 단계 이전 설정을 유지하며 다른 단계 설정과 Async 제한 시간은 독립적이다.
- **SC-007**: 최상위 클래스명 초기 설정·단계별 변경·잘못된 설정 복구·내장 및 중첩 설정·코드 교체 후 최신 설정·중앙 직렬화 회귀가 통과한다.

명확화: 최신 요청은 기존 Async.step·steps 설정 중계 계약을 대체한다. Pipeline의 클래스명 설정 전달과 _LiveConfig 감시를 내부 Step에도 적용한다. 같은 클래스의 내부 인스턴스는 동일 섹션을 사용한다. 생성자 timeout_ms는 YAML에 없으면 유지한다. 추가 질문은 필요하지 않다.

## 공통 모델 CUDA 스트림

- FR-025: CudaAsync 작업자는 장치별 모델 스트림을 생성·재사용하고 입력 생산 완료 이후 내부 Step 전체를 그 스트림에서 실행한다. 원본 cuda_stream은 유지하며 요청 종료·오류에서 모델 스트림 완료를 보장한다.
- FR-026: YoloDetect 개별 모드·TensorRTInference·예제 전후처리는 실행 문맥의 모델 스트림을 재사용한다. 단독 실행은 기존 별도 스트림과 준비 확인을 유지한다. 실행 문맥은 입력 속성에 강제 노출하지 않고 요청 범위로 격리한다.
- SC-009: 복수 Step의 동일 모델 스트림·영상 스트림 보존·요청 문맥 격리 및 실제 YOLO·TensorRT·전후처리 회귀가 통과한다.

명확화: YOLO batch=True의 local_yolo 공유 배치 작업자는 다른 요청과 묶이므로 기존 작업자 스트림을 유지한다. 공통 스트림은 해당 Step의 배치 입력 준비에 적용된다. 추가 질문은 필요하지 않다.
