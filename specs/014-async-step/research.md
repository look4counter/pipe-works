# 설계 조사

## 지속 입력 스트림

**결정**: 작업자 하나가 감싼 `Step.process`의 반복자를 유지한다.

**근거**: `enumerate(inputs)`에 보관하는 지역 상태를 유지해야 한다.

**대안**: 입력마다 새 반복자를 만들면 카운터가 초기화된다.

## 원본 격리

**결정**: 후속 사용자 요청에 따라 작업 시작 시에는 속성 사전만 분리하고 읽기 전용 데이터를 공유한다. 타임아웃 때만 후속 전달용 데이터를 깊은 복사하고 텐서를 복제한다.

**근거**: 정상 경로의 보호용 복사를 제거한다. 결과 속성 변경은 작업 컨텍스트에만 남기고 타임아웃 후 다음 단계의 변경은 복사본에서 수행한다. 이미 실행 중인 작업의 입력을 바꿀 수 없으므로 복사 방향은 후속 전달 쪽이다. 타임아웃 복사 실패 시 실행 중 작업을 기다리는 안전한 복구를 사용한다.

**대안**: 데이터 제자리 수정을 허용하면서 사전 복사까지 없애는 방식은 실패 시 롤백을 보장하지 못한다. 따라서 공유 입력은 읽기 전용으로 제한한다.

**수명 근거**: [NVIDIA 공식 DLPack 안내](https://docs.nvidia.com/video-technologies/pynvvideocodec/pynvc-api-prog-guide/using_pynvvideocodec_apis.html)에 따르면 PyNvVideoCodec 프레임은 사용하는 텐서가 파괴될 때까지 메모리 소유권을 유지한다. 요청은 가져온 텐서를 완료까지 보관한다. 외부 공급자의 수명 계약도 동일하게 요구한다.

## 종료와 실패

**결정**: 슬롯을 닫고 무한 대기는 하지 않는다. 예외 후 다음 요청에서 처리 스트림을 재생성한다.

**근거**: 스레드나 GPU 작업을 안전하게 강제 취소할 수 없다. 완료 후 작업자에서 자원을 정리한다.

## 모듈 이름

**결정**: 후속 사용자 요청에 따라 `async_step.py`로 변경하고 일반 가져오기 구문으로 공개한다.

**근거**: `async`는 예약어이지만 `async_step`은 일반 가져오기 구문에 사용할 수 있다. 클래스 이름과 처리 동작은 유지한다.
