# 무복사 디코더 조사

## 다단계 비동기 정체 재현

실제 NVDEC와 세 단계 CudaAsync, 1ms 타임아웃 및 유한한 200개 입력 조합에서 작업자가 멈췄다. Tap을 포함한 회귀 검증에서는 입력 42개·출력 33개에서 정체를 재현했다. 잠금 주소는 4개이고 반환 예약은 0개였다. 스택 조사에서 Tap 보관 프레임, CudaAsync의 이전 성공 결과 속성 사전, 폐기 입력 및 후속 소비 프레임이 각각 버퍼를 보관했다. 단계 생성기도 yield 시점의 내부 컨텍스트를 보관한다.

결정: 이전 성공 결과의 임시 속성 사전을 즉시 해제하고, 버리거나 전달을 마친 입력·요청의 반복자 지역 참조를 다음 입력 요청 전에 해제한다. 완료 요청의 원본 참조도 내부 작업 컨텍스트에서 정리한다. 결과 컨텍스트를 먼저 분리해 출력과 외부 텐서 수명은 유지한다. 내부 정리만 제거하면 입력 166개에서 다시 멈췄고, 지역 참조 정리만 제거해도 멈췄으므로 두 경로가 필요하다. 잠금 상한을 확대하는 방안은 선택하지 않는다.

- 결정: 실제 2.2.2의 GetNumDecodedFrame → GetLockedFrame → UnlockFrame 경로를 사용한다. 반환형은 원시 GPU 주소다. GetFrame과 Decode 결과는 DLPack 텐서를 보관해도 후속 디코딩이 같은 주소를 덮어쓰는 것을 실제 NVDEC에서 확인했다. 문서의 메모리 소유권 설명을 풀 재사용 방지로 해석하지 않는다.
- 근거: [NVIDIA Decoder API](https://docs.nvidia.com/video-technologies/pynvvideocodec/pynvc-api-reference/decoder.html), [DLPack 가이드](https://docs.nvidia.com/video-technologies/pynvvideocodec/pynvc-api-prog-guide/using_pynvvideocodec_apis.html), 설치된 2.2.2 바인딩과 실제 NVDEC 실험.
- 결정: 잠금 GPU 주소는 공개 CUDA Array Interface와 torch.as_tensor로 공유한다. 텐서 주소가 원본과 동일하며 뷰 객체는 텐서 저장소가 끝날 때까지 유지된다. DLPack 재공유에도 수명이 이어짐을 weakref 실험으로 확인했다. 사설 PyTorch storage API와 자체 DLPack C 구조체는 사용하지 않는다.
- 결정: 매 프레임 CPU 동기화를 제거하고 GPU 이벤트로 준비와 사용 완료를 연결한다. 잠금 주소 전체 4개 상한과 이벤트 반환 예약을 둔다. 종료·상한 대기는 허용한다.
- 결정: 실제 PyNvDecoder에는 Flush가 없으므로 빈 PacketData로 EOF를 처리한다. 기존 불투명 모의 디코더의 Decode/Flush는 호환 경로로 유지한다.
- 검증: 256×256 NV12 실제 NVDEC → 잠금 주소 → 공유 PyTorch 텐서 → NVENC에서 15프레임을 처리했다. 첫 버퍼를 보관한 채 후속 디코딩을 진행해도 내용이 유지되고 인코더가 공유 텐서를 받았다.
- 환경: 패키지 디렉터리와 torch/lib를 os.add_dll_directory에 명시하면 로컬 NVDEC/NVENC를 실행할 수 있었다. 이전 DLL 누락 판단은 일반 import 설정에 관한 것이며 하드웨어 검증 불가능을 의미하지 않는다.

## 실제 예제 정체 수정과 큐 확대

이전 수정에서 핫스왑·Tap의 완료 출력과 BoxOverlay 뷰 참조를 정리했다. 실제 예제를 송출 없이 60초 실행하여 1,108개 출력을 확인했다. 이번 사용자 요청으로 큐를 30개 FIFO, 잠금 상한을 34개로 확대한다. 가득 찬 큐의 오래된 대기 프레임을 버퍼 획득 전에 해제한다. 실제 NVDEC 검증은 80개 입력을 사용하고 소비 중인 첫 프레임을 유지한 채 70개 이상 게시해 큐 포화 시에도 진행하는지 확인한다.

## GPU 메모리 부족의 추가 재현

30개 큐로 실제 카메라를 디코딩만 했을 때 프레임 크기는 460,800바이트였고 잠금 31개, 가용 GPU 메모리 약 7,022MiB로 안정적이었다. 반면 TensorRT를 포함한 예제는 약 60프레임마다 PyTorch 예약 메모리가 160~180MiB씩 증가했다. 예외 위치가 NVDEC라고 해서 디코더 큐의 크기만 원인이라고 판단할 수 없다.

실제 TensorRT 엔진에 기존 할당기 등록을 반복한 실험에서 10/20/30/40회 추론 후 생존 할당기는 10/20/30/40개, PyTorch 할당 메모리는 31/58/85/112MiB였다. 가비지 수집으로도 없어지지 않았으며 실행 컨텍스트 종료 후에만 모두 해제됐다. 세션은 바인딩별 할당기를 한 번만 등록하고 매 실행 버퍼 상태를 초기화하도록 수정한다. 이전 출력 텐서를 보관할 때 그 내용이 유지되도록 매 실행 버퍼 저장소는 분리한다.

수정 후 같은 실제 엔진의 40/500/1,000회 추론에서 생존 할당기 1개, PyTorch 할당 7MiB, 예약 40MiB로 일정했다. 이는 TensorRT와 디코더를 포함한 전체 GPU 사용량이 아니라 PyTorch 측 계측 값이다. 사용자의 오류 순간 메모리 상태는 없어 다른 동시 GPU 사용 가능성까지 배제하지 않는다.
