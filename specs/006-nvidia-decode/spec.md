# 기능 명세: 최신 프레임 NVIDIA 디코딩

## 압축 패킷 복사 제거 (2026-10-10)

- FR-015: 입력 PyAV 패킷의 압축 데이터를 별도 Python 바이트나 ctypes 버퍼로 복사하지 않고 디코더에 전달한다. 디코더 호출 반환까지 원본 패킷을 보관하고 길이·PTS·오류·EOF 계약을 유지한다.
- SC-010: 원본 주소와 길이가 디코더에 그대로 전달되고 바이트 변환을 금지해도 동작한다. 실제 GPU 디코딩과 RTSP 입력·송출 회귀 검증을 통과한다.

명확화: NvidiaDecode의 압축 입력 전달만 변경한다. RTSPSource의 PyAV 패킷과 RTSPPublish의 직접 소비 계약, 영상 출력 수명 정책은 유지한다. 추가 질문이 필요한 불명확성은 없다.

**작성일**: 2026-10-09
**상태**: 명세 확정
**입력**: NvidiaDecode 내부에서 수신·디코딩과 후속 처리를 스레드로 분리하고 최대 30개 대기 프레임을 순서대로 사용한다.

## 사용자 시나리오와 검증

### 사용자 이야기 1: 느린 후속 처리에도 최신 영상 유지 (우선순위 P1)

운영자는 기존 NvidiaDecode 뒤에 추론 또는 인코딩을 연결한다. 후속 처리가 느려도 입력 패킷은 계속 소비되고 대기 프레임은 30개까지 보관하고 초과 시 가장 오래된 대기 프레임을 버린다.

**독립 검증**: 첫 프레임 처리 중 생산자가 여러 프레임을 만든 뒤 다음 출력이 남은 큐의 가장 오래된 프레임인지 확인한다.

**인수 조건**:

1. 생산 작업자가 압축 패킷을 순서대로 디코딩하며 임의로 압축 패킷을 버리지 않는다.
2. 대기 프레임은 최대 30개다. 가득 차면 가장 오래된 대기 프레임을 제거하고 새 프레임을 추가한다.
3. 이미 후속 처리 중인 프레임은 수정하거나 재사용하지 않는다.
4. GPU 번호, 패킷 바이트와 PTS, 프레임 컨텍스트 필드는 기존 계약을 유지한다.

### 사용자 이야기 2: 오류와 종료를 안전하게 전달 (우선순위 P2)

운영자는 종료·취소·수신 실패 시 작업자가 정리되고 원인이 호출자에게 전달되기를 원한다.

**독립 검증**: 생산자 오류, 입력 종료, 소비자 조기 종료와 실행 통계 격리를 검증한다.

**인수 조건**:

1. 정상 EOF에서 지연 프레임을 회수하고 동일한 최신 프레임 정책을 적용한다.
2. 입력 또는 디코딩 오류를 원래 호출자에 전달한다.
3. 소비자 종료를 생산자에 알리고 수신 읽기가 반환한 뒤 생산자에서 입력을 정리한다.
4. 실행별 수신 통계와 핫스왑 입력 구간 경계를 유지한다.

## 요구사항

- FR-001: 설정 GPU 번호와 지원 코덱 선택, 패킷 바이트·PTS 전달을 유지한다.
- FR-002: 생산 스레드가 입력 소비와 디코딩을 맡고 기존 process 반복자는 대기 프레임을 FIFO 순서로 후속 Step에 전달한다.
- FR-003: 미소비 대기 프레임은 최대 30개이며 초과 시 가장 오래된 프레임을 제거한다. 모든 입력 프레임 전달은 더 이상 보장하지 않는다.
- FR-004: 전달 중인 프레임을 이후 디코딩과 분리하여 영상 데이터가 변하지 않게 하고 GPU 완료와 버퍼 수명을 보장한다.
- FR-005: 출력은 frame, video_stream, cuda_stream, pixel_format, processing_started_at을 유지한다. 시작 시각은 후속 처리에 전달하는 시점이다. 디코딩 출력 게시 시각과 대기 프레임 폐기 건수도 확인할 수 있게 한다. 게시 시각은 GPU 작업 완료 시각이 아니다.
- FR-006: 정상 EOF의 지연 프레임에도 동일한 정책을 적용하고 빈 입력은 정상 종료한다.
- FR-007: 오류를 호출자에 전달하고 소비자 취소 시 작업자 본인이 입력을 정리한다. 실행 중인 반복자를 다른 스레드에서 닫지 않는다.
- FR-008: 수신 작업자의 실행 통계 맥락을 유지하고 핫스왑 복구용 목록이 백그라운드 패킷을 무제한 보관하지 않게 한다.
- FR-009: 기존 Step 사용법을 유지하고 문서와 모의·CUDA 검증을 갱신한다.
- FR-010: 디코딩 출력 프레임을 별도 영상 메모리로 복사하지 않고 원본 버퍼의 수명을 유지한다. 소비 중인 프레임과 최신 대기 프레임을 구분하며 GPU 사용 완료 전 원본을 반환하지 않는다.
- FR-011: 매 프레임 생산·소비 경계에서 CPU가 GPU 전체 스트림 완료를 기다리지 않는다. GPU 이벤트로 준비·사용 완료를 연결하며 미완료 해제 대기량은 고정 상한을 가진다. 종료와 상한 도달 시 안전을 위한 대기는 허용한다.
- FR-012: 다단계 CudaAsync 요청 완료 후 내부 작업 컨텍스트의 원본 프레임 참조가 누적되어 디코더 잠금 상한에서 멈추지 않아야 한다. 출력 소비자와 미완료 요청이 사용 중인 프레임은 계속 보호한다.
- FR-013: 핫스왑과 Tap은 전달·소비가 끝난 출력의 내부 참조를 다음 입력 대기 전에 해제한다. 실제 예제의 메타데이터·추론·보고서·그리기·지연 Tap·인코딩 조합에서도 프레임 진행을 유지한다.
- FR-014: 연속 추론에서 이미 사용한 TensorRT 출력 할당기 때문에 GPU 메모리가 추론 횟수에 비례해 누적되지 않아야 한다. 외부에서 보관한 이전 출력 텐서의 내용은 유지한다.

## 성공 기준

- SC-001: 소비자가 멈춘 동안에도 생산자가 패킷을 진행하며 다음 출력은 남은 큐의 가장 오래된 프레임이다.
- SC-002: 대기 프레임이 30개를 넘지 않고 소비 중 프레임 내용은 유지된다.
- SC-003: 코덱·PTS·컨텍스트·지연 프레임 회수·오류·취소와 실행별 통계를 검증한다.
- SC-004: GPU 디코더 프레임을 보관하거나 소비자가 느려져도 대기 목록이 계속 늘어나지 않는다.
- SC-005: 실제 디코더가 추가 프레임을 생성하는 동안 공유 출력의 GPU 주소와 기존 영상 내용이 유지된다. 큐 게시 과정에서 영상 복사가 발생하지 않는다.
- SC-006: 완료 이벤트가 미완료인 동안 버퍼를 보호하고 완료 후 해제하며, 일반 프레임 전달에서 CPU 스트림 동기화를 호출하지 않는다.
- SC-007: 실제 디코더와 세 단계 비동기 처리 조합이 타임아웃·부분 종료를 겪어도 유한한 입력을 끝까지 소비하거나 명시적 취소로 종료한다. 완료된 요청 내부 참조 때문에 FPS가 영구히 0이 되지 않는다.
- SC-008: 실제 예제와 같은 후속 단계 조합을 연결한 검증에서 지연 Tap이 여러 입력을 소비하는 동안 디코딩과 출력이 계속 진행한다. 실제 카메라 검증과 네트워크 없는 재현 검증을 구분해 기록한다.
- SC-009: 이전 출력을 보관하지 않는 실제 엔진 반복 추론 1,000회에서 준비 완료 후 GPU 할당량이 추론 횟수에 비례하여 증가하지 않는다. 출력 바인딩별 할당기 등록 수는 하나로 유지된다.

## 가정과 명확화

사용자는 최신 영상 유지와 프레임 생략을 명시적으로 선택했다. 별도 LatestFrame Step이나 옵션 없이 기본 동작을 변경한다. 추가 질문이 필요한 중대한 모호성은 없다. 입력의 디코딩 속도가 수신 속도보다 느리면 이 구조만으로 최신성을 보장하지 못한다. 이미 수신 버퍼에 쌓인 데이터의 재연결 복구는 별도 범위다. 취소 중 네트워크 읽기는 기존 RTSP timeout_ms가 끝나거나 패킷이 도착해야 반환한다. 인코더 타임스탬프 정책 변경은 이번 범위가 아니다.

### 복사 제거 명확화

사용자는 2026-10-09 추가 요청에서 복사 없는 안전한 프레임 전달을 선택했다. 소비 중 버퍼는 보호하고 다른 버퍼로 최신화를 계속한다. 직접 할당한 버퍼 두 개를 디코더에 주입하는 방식은 필수가 아니며, 디코더 소유 버퍼를 빌리고 반환하는 방식도 충족한다. 디코더 내부 버퍼 전체 수는 제한 대상이 아니다. 실제 FPS 회복 수치는 입력과 GPU 부하에 의존하므로 보장하지 않는다.

### 2026-10-10 실행 경로 명확화

사용자는 같은 프로젝트에서 `.venv\Scripts\python.exe examples\01_single_stream_rtsp_style.py`로 실행했다고 확인했다. 송출을 제외한 실제 예제 실행 경로에서도 잠금 4개와 반환 대기 0개 상태에서 생산자가 멈춤을 재현했다. 이전 비동기 단독 검증만으로 예제 전체의 문제가 해결됐다고 판단하지 않는다.

### 30개 큐 명확화

사용자는 현재 디코딩된 프레임 큐를 30개로 확대하도록 지시했다. FIFO로 소비하고 초과 시 가장 오래된 대기 프레임을 폐기한다. 여러 디코딩 출력과 EOF 출력도 순서대로 큐에 넣는다. 무복사와 GPU 완료·외부 참조 보호 계약은 유지한다.
