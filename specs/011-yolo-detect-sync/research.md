# 비동기 GPU 감지 연구

- 결정: 기존 배치 단계의 GPU NV12 변환·패딩·예측기를 단일 단계에서 재사용한다.
- 근거: 설치된 Ultralytics 기본 `DetectionPredictor.postprocess`는 텐서 원본을 NumPy로 변환한다. 텐서 입력만 제공해서는 CPU 복사를 막을 수 없다. 기존 GPU 예측기는 이 변환을 우회한다.
- 검토한 대안: CPU OpenCV 경로는 복사 금지 조건에 어긋나고, 공유 배치 큐를 호출하면 단일 모델·단일 프레임 계약이 바뀐다.
- 결정: 입력 스트림에서 GPU 복제와 준비 이벤트를 기록하고 작업자 전용 CUDA 스트림에서 변환·추론·좌표 복원을 수행한다. 원본 표면 소유자를 요청 완료까지 보관한다.
- 근거: 디코더·인코더는 영상 스트림을 공유하므로 Python 작업자만 분리하면 영상 GPU 작업이 추론 뒤에 배치된다. 준비 이벤트와 별도 스트림으로 순서와 메모리 수명을 보장한다.
- 결정: 표시·저장 기능은 끈다. 결과는 원본 해상도 GPU RGB 영상과 GPU 박스 텐서를 포함한다.
- 근거: 표시·저장 과정의 CPU 변환을 차단하고 배치 결과와 같은 계약을 제공한다.
- 결정: 최대 1개 슬롯과 데몬 작업자를 사용하고 종료에서 join하지 않는다. 기존 살아 있는 작업자를 재실행에서 재사용하거나 종료 중에는 우회한다.
- 근거: 실행 중 CUDA 호출은 스레드에서 안전하게 강제 취소할 수 없다. 요청·스레드를 추가하지 않으면 영구 정지에도 메모리와 작업자 수가 제한된다. 실행 종료를 기다리는 일반 실행기 대신 명시적 수명 관리를 사용한다.
- 결정: 요청 시 실행 문맥을 복사하여 추론 통계를 기록한다.
- 근거: `StreamReport`는 ContextVar를 사용하므로 새 스레드에서 그대로 기록하면 실행 통계가 섞인다.
- 결정: 기존 배치 YAML과 동일한 동명 파일·밀리초 단위를 사용한다. 단일 단계에서는 추론 결과 대기 제한으로 해석한다.
- 근거: 사용자가 설정 위치를 지정했다. 배치의 요청 수집 제한과 단일 감지의 결과 대기 제한은 의미가 다르므로 문서에 명시한다.
