# 기능 명세: 단일 작업자 Tap

**작성일**: 2026-10-03  
**상태**: 구현 대상

## 사용자 시나리오와 검증

### 시나리오 1: 느린 후처리와 독립된 영상 전달

사용자는 오래 걸리는 일반 Step을 `Tap`로 감싸 주 영상 스트림을 지연시키지 않고 실행한다.

**인수 조건**

1. `Tap(PostProcess())`로 구성할 수 있다.
2. 입력 프레임은 후처리 완료를 기다리지 않고 동일 객체로 다음 Step에 전달된다.
3. 후처리 작업은 동시에 하나만 실행된다.
4. 작업 중 들어오는 입력은 후처리에서 건너뛰고 주 스트림에는 전달한다.
5. 작업이 끝난 후 새 입력이 오면 후처리를 다시 수행한다.

### 시나리오 2: 반복자 계약 유지

감싼 일반 Step은 입력 반복자를 한 번 받아 여러 프레임에 걸쳐 처리하며 내부 상태를 유지한다. 그 출력은 주 스트림에 합쳐지지 않는다.

### 시나리오 3: 내부 Step 핫스왑

사용자가 `PostProcess` 구현 파일을 변경하면 `Tap`의 작업자가 다음 처리 경계에서 변경된 구현을 사용한다. 주 스트림은 계속 전달된다.

## 기능 요구사항

- **FR-010**: 배경 후처리 단계의 공개 이름을 `Tap`으로 변경하고 사용 예제·설정·문서에서도 같은 이름을 사용한다. 이전 `Tap` 별칭은 제공하지 않는다.
- **FR-011**: 이름 변경 후에도 입력 전달·단일 작업자·건너뛰기·종료·핫스왑·설정 갱신·중앙 실행 출력 전달 동작을 유지한다.

- **FR-001**: `Tap`는 생성자에서 일반 Step 하나를 받아야 한다.
- **FR-002**: 감싼 Step의 `process()`는 코드 변경이나 상류 구간 변경이 없으면 Tap 처리 구간에서 한 번 호출해야 한다.
- **FR-003**: 감싼 Step이 이전 입력 처리 중이면 새 입력을 맡기지 않아야 한다.
- **FR-004**: 모든 입력 컨텍스트를 동일 객체로 한 번씩 다음 Step에 전달해야 한다.
- **FR-005**: 감싼 Step의 출력은 소비하되 주 스트림으로 반환하지 않아야 한다.
- **FR-006**: 감싼 Step의 예외는 기록하고 주 스트림은 계속 전달해야 한다.
- **FR-007**: 입력 스트림 종료 또는 닫기 요청 시 새 작업 수락을 중단해야 한다.
- **FR-008**: 사용자 정의 내부 Step의 소스 파일 변경을 감지하여 기존 핫스왑 방식으로 구현을 교체해야 한다. 내장 Step은 자동 교체에서 제외한다.
- **FR-009**: 이미 핫스왑된 Step을 전달받으면 중복으로 감싸지 않아야 한다.

## 성공 기준

- **SC-006**: 사용자가 `Tap(PostProcess())`와 `Tap` 설정 섹션으로 기존 후처리 동작을 실행할 수 있다.
- **SC-007**: 관련 회귀 검증에서 이름 변경으로 인한 실패가 없다.

- **SC-001**: 후처리가 멈춰 있는 동안에도 이후 입력 프레임은 출력된다.
- **SC-002**: 후처리 중 들어온 입력은 후처리 호출 횟수를 늘리지 않는다.
- **SC-003**: 후처리 완료 뒤 다음 입력은 후처리로 전달된다.
- **SC-004**: 감싼 Step은 같은 처리 구간에서 반복자 하나를 사용한다.
- **SC-005**: 내부 Step 파일 변경 후 다음 수락된 입력은 새 구현으로 처리된다.

## 명확화: 2026-10-09

사용자가 이름 변경을 승인했다. 모듈은 `tap.py`, 클래스는 `Tap`으로 변경한다. 동작 변경이나 이전 이름 호환 계층은 범위에 포함하지 않는다. 일반적인 최종 출력 단계 분류인 Sink 용어는 유지한다. 추가 질문이 필요한 불명확성은 없다.

## 가정과 범위

- 감싼 Step이 다음 입력을 요청하는 시점을 이전 입력 처리가 끝난 시점으로 본다.
- 감싼 Step은 주 스트림의 컨텍스트를 읽기 전용으로 다룬다.
- 출력 프레임 결합, 후처리 결과 저장, 다른 소스 파일 변경은 범위 밖이다.
