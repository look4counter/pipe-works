# 연구 결과

## 결정: 실제 실행 스레드 종료 대기

근거: src/pipeworks/main.py의 _handle은 현재 finished.wait(10) 결과를 확인하지 않고 반환한다. handle_client는 반환 즉시 활성 연결 수를 줄여 1초 유휴 타이머를 시작한다. 실행 스레드는 daemon이므로 서버 종료가 정리를 중단할 수 있다.
Thread.join은 실제 스레드 종료를 기다리므로 결과 전송과 정리까지 포함한다. 감시 루프 finally에서 실행해 예외 경로도 보장한다. 기존 요청별 스레드 구조 덕분에 다른 요청 수락은 막지 않는다.

대안: 시간 제한만 늘리는 방법은 임의의 긴 정리에서 재발하므로 제외한다. finished.wait만 무기한 대기하면 완료 신호 이전 정리 예외와 실제 스레드 종료 간 차이를 다루지 못하므로 실제 Thread를 기다린다. 별도 전역 활성 실행 레지스트리는 기존 활성 연결 수로 해결할 수 있어 추가하지 않는다.

기술적 미해결 사항이 없고 기존 표준 라이브러리를 유지하므로 별도 외부 조사나 연구 위임은 필요하지 않다.
