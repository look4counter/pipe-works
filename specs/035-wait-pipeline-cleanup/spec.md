# 기능 명세: 중앙 프로세스의 실행 정리 완료 대기

**작성일**: 2026-10-16
**상태**: 명세 검증 완료
**요청**: 클라이언트 연결 종료 후 작업자가 실행 중인데 유휴 종료될 수 있는 문제를 해결한다.

## 사용자 시나리오 및 검증

### 사용자 스토리 1 — 느린 정리 중 실행 유지 (P1)

운영자는 클라이언트가 연결을 끊어도 진행 중인 파이프라인의 중단 처리와 리소스 정리가 끝날 때까지 중앙 프로세스가 살아 있기를 원한다.
우선순위 이유: 정리 중인 GPU·네이티브 작업의 조기 종료를 방지한다.
독립 검증: 중단 후 정리를 12초 이상 보류하고 중앙 프로세스 생존을 확인한 뒤 정리를 허용해 종료를 확인한다.

1. 연결이 끊기거나 생존 신호가 만료되면 중단 신호를 전달한다.
2. 기존 10초 대기와 1초 유휴 시간이 지나도 정리 중인 실행 때문에 서버는 종료하지 않는다.
3. 정리를 끝내면 해당 실행을 종료하고 마지막 실행이면 기존 유휴 종료 정책을 따른다.

### 사용자 스토리 2 — 다른 실행과 정상 완료 유지 (P2)

운영자는 느린 정리 대기가 다른 요청이나 정상 실행 완료를 막지 않기를 원한다.
우선순위 이유: 중앙 프로세스의 다중 실행 동작을 보존한다.
독립 검증: 정리를 보류한 상태에서 새 요청을 처리하고, 마지막 정리가 끝난 뒤 서버 종료를 확인한다.

1. 정리 대기는 해당 요청에만 적용되고 새 연결과 생존 확인 요청은 처리된다.
2. 정상 완료의 결과·오류 응답 및 운영·개발 그룹 분리는 유지된다.

### 경계 조건

- 연결 EOF와 생존 신호 만료, 정상 완료 직후 응답 전송 실패를 포함한다.
- 연결 감시 중 예외가 나도 작업자 종료 전에 실행 수를 감소시키지 않는다.
- 리소스 정리가 영구히 멈추면 중앙 프로세스도 유휴 종료하지 않는다. 강제 종료 정책은 이번 범위에 추가하지 않는다.

## 요구사항

### 기능 요구사항

- **FR-001**: 연결 종료·생존 신호 만료 시 기존 중단 신호 전달을 유지한다.
- **FR-002**: 요청 처리는 해당 파이프라인 실행 작업자의 실제 종료까지 유지하고 고정 시간 경과로 정리 완료를 간주하지 않는다.
- **FR-003**: 정리 중 실행은 유휴 종료 판단의 활성 실행 수에 포함한다.
- **FR-004**: 정상·오류 완료의 응답과 새 요청 수락 및 그룹 분리를 보존한다.
- **FR-005**: 연결 감시 예외에도 작업자 종료 대기를 보장하고 느린 정리의 서버 생존·정리 후 종료에 대한 회귀 검증을 추가한다.
- **FR-006**: 정리 대기의 시간 제한 제거와 정리가 끝나지 않을 때의 동작을 사용자 문서에 설명한다.

### 주요 엔터티

- 실행 요청: 연결과 해당 파이프라인 실행 작업자를 소유하며 작업자 종료 후에만 활성 상태를 해제한다.
- 중앙 프로세스: 활성 요청이 없을 때 기존 유휴 지연 후 종료한다.

## 성공 기준

- **SC-001**: 연결 해제 후 정리를 12초 이상 지연해도 서버가 생존하며 정리 완료 표시를 남기기 전에 종료하지 않는다.
- **SC-002**: 정리를 보류한 상태에서 별도 실행의 완료 응답을 수신한다.
- **SC-003**: 정리가 완료되면 마지막 요청 해제 후 기존 유휴 종료가 동작하며 관련 중앙 프로세스 검증이 모두 통과한다.

## 가정 및 범위

- 앞선 조사에서 재현한 1번 문제만 수정한다. GPU 오류 복구와 병렬 송신 패킷 공유는 별도 범위다.
- 파이프라인 실행 함수가 담당하는 정리 완료를 기다린다. 개별 비동기 단계의 별도 수명 계약을 바꾸지는 않는다.
- 종료하지 않는 네이티브 호출을 임의로 끊는 기능은 추가하지 않는다.
