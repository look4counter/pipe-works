# 기능 명세: 단계별 YAML 설정과 동적 컨텍스트

**기준**: 현재 `src/pipeworks/pipeline.py`, `models.py`, `hotswap.py` 동작

## 사용자 시나리오

사용자는 YAML 경로로 `Pipeline`을 만들고 `.step(단계 인스턴스)`로 단계를 등록한다. 각 단계의 클래스명과 같은 섹션이 `SimpleNamespace`로 변환되어 등록 시 `configure()`에 전달된다. 사용자 정의 단계는 핫스왑 래퍼가 설정을 별도로 보관하여 교체 후 다시 적용한다. 실행 중 YAML을 수정하면 기존 파이프라인 연결을 끊지 않고 변경된 단계 설정을 다음 처리 경계부터 적용한다.

## 기능 요구사항

- **FR-001**: 파이프라인은 생성 시 YAML을 읽어 최상위 매핑과 모든 섹션의 매핑 구조를 검증해야 한다. 빈 파일은 빈 설정으로 취급한다.
- **FR-002**: 파이프라인의 설정은 속성형 객체이며, 등록 단계의 섹션은 원래 단계의 클래스명으로 선택해야 한다. 섹션이 없으면 빈 설정 객체를 전달한다.
- **FR-003**: `Pipeline.step()`은 원래 단계의 `configure(SimpleNamespace)`를 호출하고 등록 연쇄 호출을 지원해야 한다. `Pipeline.process` 별칭은 제공하지 않는다.
- **FR-004**: `Step`은 `process(inputs)` 추상 메서드와 기본 `configure(config)`를 제공한다. 기본 구현은 설정 저장을 강제하지 않으며, 각 단계가 필요한 값을 개별 속성에 저장한다.
- **FR-005**: 사용자 정의 단계의 핫스왑 래퍼는 전달받은 설정을 보관하고 코드 교체 또는 상류 재시작 시 다시 적용해야 한다. 내장 단계의 자동 감시는 제외한다.
- **FR-006**: `PipelineContext`는 고정 필드가 없는 `SimpleNamespace` 기반 객체로, 생성 시와 생성 후 임의 속성을 받을 수 있어야 한다.
- **FR-007**: 같은 컨텍스트 객체를 전달하는 단계에서는 추가한 속성이 유지된다. 디코더·인코더처럼 새 출력 객체를 만드는 단계에는 임의 속성 자동 승계를 요구하지 않는다.
- **FR-008**: RTSP 소스는 설정된 전송 방식, 제한 시간, 재연결 정책과 간격을 사용해야 한다. 중앙 실행의 중단 이벤트가 전달되면 재연결 대기에서 깨어나야 한다.
- **FR-009**: 실행 중 YAML 내용이 바뀌면 재시작 명령 없이 유효한 변경을 감지하고, 값이 달라진 섹션의 단계에 새 설정을 적용해야 한다. 내용이 같은 저장이나 다른 섹션의 변경은 해당 단계를 다시 시작하지 않아야 한다.
- **FR-010**: 새 설정은 현재 처리 중인 입력을 마친 뒤 기존 Step 인스턴스의 `configure()`를 다시 실행해 적용해야 한다. 설정 변경만으로 처리 반복자, 소스 연결, 디코더·인코더, 송출 연결을 종료하거나 재시작하면 안 된다.
- **FR-011**: 잘못된 YAML이나 매핑 구조는 현재 유효한 설정과 파이프라인 실행을 유지해야 한다. 단계의 `configure()`가 실패해도 해당 단계는 이전 구현과 설정으로 계속 처리해야 한다.
- **FR-012**: 사용자 정의 Step의 코드 변경과 설정 변경이 함께 발생해도 유효한 최신 코드와 설정을 적용하고 입력을 잃지 않아야 한다. 코드 변경은 기존 교체 계약을 따른다. `Tap` 내부 사용자 Step에도 같은 설정 갱신 규칙을 적용해야 한다.
- **FR-013**: RTSPSource와 RTSPPublish의 제한 시간 설정·속성은 밀리초 단위 `timeout_ms`여야 한다. 기본값은 5000이며 유한한 0 이상의 숫자를 허용하고 불리언·문자열·음수·비유한 값을 거부한다. 이전 `timeout` 옵션은 구성 오류로 거부한다.
- **FR-014**: 수신·송출 연결에는 각각 라이브러리가 요구하는 단위로 환산해야 한다. 예제·현재 사용 안내도 `timeout_ms`로 바꾸고 기존 대기 시간을 보존해야 한다. 재연결 간격과 모델별 제한 시간 설정은 유지한다.

## 성공 기준

- **SC-001**: 빈 파일, 누락 섹션과 잘못된 최상위·하위 구조의 처리 결과가 등록 전에 확인된다.
- **SC-002**: 서로 다른 단계 인스턴스가 자기 클래스명 섹션의 값만 적용받고 사용자 단계 교체 후에도 설정이 다시 적용된다.
- **SC-003**: 빈 컨텍스트에 고정된 패킷·스트림 필드가 없으며 임의 속성을 추가할 수 있다.
- **SC-004**: 동일 객체 전달 단계에서 임의 속성이 유지되고 새 출력 객체를 만드는 단계와 구분된다.
- **SC-005**: RTSP 소스의 설정과 중앙 실행 중단 이벤트가 연결·재연결에 적용된다.
- **SC-006**: 별도 프로세스에서 실행 중인 파이프라인의 YAML 값을 바꾸면 해당 단계의 후속 입력에서 새 값이 관찰되고, 다른 섹션의 단계는 다시 시작하지 않는다.
- **SC-007**: 잘못 저장한 YAML과 단계 설정 오류 뒤에도 이전 값으로 처리가 이어지며, 올바른 값을 다시 저장하면 새 설정이 적용된다.
- **SC-008**: `Tap` 내부 Step과 입력 없는 소스 Step도 설정 변경을 처리 경계에서 적용한다.
- **SC-009**: 설정 변경 전후에 Step 인스턴스와 실행 중인 처리 반복자의 식별자가 유지되고, 소스 및 송출 연결을 닫지 않은 채 후속 입력이 처리된다.
- **SC-010**: 두 RTSP 단계의 기본값 5000ms와 0·250·1250.5ms가 올바른 연결 제한 시간으로 환산된다. `timeout_ms: 10000`은 기존 10초와 같은 동작을 유지한다.
- **SC-011**: 이전 옵션과 잘못된 값은 등록 시 거부되고, 예제 YAML의 두 RTSP 섹션과 현재 문서는 밀리초 설정을 사용한다. 기존 RTSP 및 구성 테스트에 새 오류가 없어야 한다.

## 후속 사용자 시나리오: RTSP 제한 시간 밀리초 통일 (우선순위 P1)

사용자는 2026-10-09 요청에 따라 RTSPSource와 RTSPPublish의 설정을 `timeout_ms`로 바꾸고 밀리초로 지정한다. 독립 검증은 모의 연결의 전달값으로 수행한다. 250ms를 지정하면 수신·송출의 실제 대기 시간이 모두 0.25초에 해당해야 한다. 기본값과 기존 예제의 실질 대기 시간은 보존한다.

## 명확화: 2026-10-09

추가 질문이 필요한 모호성은 없다. 기본 5초는 5000ms로 유지하고 예제 수치는 1000배로 환산한다. 이전 이름의 조용한 무시나 초 단위 별칭은 제공하지 않는다. 재연결 간격은 계속 초 단위이다. 이 후속 계약은 기존 RTSP 문서의 초 단위 사용자 옵션 계약을 대체한다.

## 범위

YAML 섹션 이름은 단계 클래스명과 정확히 같다. `configure()` 호출은 등록 시와 유효한 설정 변경 시 발생한다. 단계가 보관할 설정 값의 종류는 각 단계의 계약에서 정한다. 외부 입출력 호출이 끝나지 않은 동안에는 변경 적용을 기다리며, 단계 목록과 순서 변경은 자동 반영하지 않는다. 이미 생성된 외부 자원의 생성 옵션은 해당 자원이 자연스럽게 다시 만들어질 때 적용될 수 있다.

`configure()` 오류 시 단계의 최상위 인스턴스 속성은 복원한다. 사용자 정의 `configure()`가 외부 자원을 직접 변경하거나 중첩 객체를 제자리 수정한 부작용은 되돌릴 수 없으므로 그런 동작은 설정 적용 계약에 포함하지 않는다.
