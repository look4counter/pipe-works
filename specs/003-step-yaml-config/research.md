# 조사: 현행 설정 전달 경계

## 후속 조사: RTSP 제한 시간

- 결정: 사용자 옵션을 밀리초 `timeout_ms`로 통일하고 기본 5000ms를 사용한다.
- 근거: 기존 기본 5초를 보존하면서 단위를 이름으로 표시한다.
- 결정: 수신은 초 튜플, 송출은 마이크로초 문자열로 변환한다.
- 근거: 설치된 PyAV의 `av.open.__doc__`는 초 단위 튜플을 명시한다. 기존 송출 구현은 FFmpeg `timeout`에 마이크로초 문자열을 전달하므로 환산만 바꾸어 같은 값을 유지한다.
- 결정: 이전 이름은 구성 오류로 거부한다.
- 근거: 이전 초 값을 밀리초로 오해하거나 조용히 무시하지 않게 한다. 별칭을 유지하는 대안은 이번 명칭 변경 요구에 맞지 않는다.

`Step.configure()`는 필수 구현 추상 메서드이며 설정 저장은 강제하지 않는다. 단계 구현체는 필요한 설정을 개별 속성에 저장한다. 사용자 정의 단계의 코드 교체 시 설정을 다시 적용하기 위해 `Hotswap`이 전달받은 객체를 별도로 보관한다. `PipelineContext`는 고정 필드가 없으므로 각 단계의 출력 계약에서 필요한 속성을 명시한다.
# 추가 조사: 실행 중 설정 변경

- 결정: 감시 기준은 파일 수정 시각 대신 내용 해시를 사용한다.
- 근거: 같은 내용으로 다시 저장했을 때 단계 재시작을 피하고, 빠르게 연속 저장한 변경도 구분한다.
- 결정: 설정 변경만 있을 때는 기존 인스턴스의 `configure()`를 실행하고 실패 시 최상위 속성을 복원하며 처리 반복자를 유지한다.
- 근거: RTSP 연결과 GPU 처리 자원을 다시 열지 않아 영상 재생 중단을 피한다.
- 고려한 대안: 새 인스턴스를 만들어 처리 구간을 다시 시작하는 방식은 활성 영상 자원을 닫으므로 채택하지 않는다.
- 제약: 현재 열린 자원이 생성 시점에 읽은 옵션은 즉시 바뀌지 않을 수 있다. 새 연결이나 새 자원이 자연스럽게 만들어질 때 반영된다.
# 후속 조사: 생성자 기본값 보존

- 결정: 최초 생성자 옵션을 별도로 보관하고 설정 시에만 YAML과 병합한다.
- 근거: 현재 값으로 fallback하면 YAML 옵션 삭제 후 이전 YAML 값이 남는다. 별도 기준은 실행 중 삭제와 재적용에도 일관된다.
- 대안: Pipeline이 모든 인스턴스 속성을 자동 전달하면 런타임 상태와 CudaAsync의 알 수 없는 키 검증이 충돌한다. 사용자 정의 configure를 자동 감싸는 방식도 기존 계약을 변경하므로 채택하지 않는다.
- 의존성: 표준 라이브러리 deepcopy를 사용하며 영상 처리 경로에 추가 작업이 없다.

## configure 필수 구현 조사

결정: 기존 abc 추상 메서드 기능을 사용한다. 근거: process의 생성 시 검증과 일관되고 구체 구현 상속을 지원한다. 호출 시 오류 방식은 잘못된 단계 생성을 허용하므로 선택하지 않는다. 미확정 사항은 없다.
