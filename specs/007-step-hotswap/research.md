# 설계 검토: Step 핫스왑

- **결정**: 사용자는 기존 `.step(...)`을 그대로 쓴다. 등록 시 설정은 원래 클래스명으로 조회하고 Step을 `Hotswap`으로 감싼다.
- **파일 확인**: 각 래퍼가 단조 시계 간격으로 자신의 클래스 소스 파일 내용을 확인한다. 기본 간격은 0.5초이며 파일이 같으면 새 모듈을 만들지 않는다.
- **코드 격리**: 새 소스는 고유한 모듈 이름으로 실행한다. 구버전 생성기가 끝나기 전에 기존 모듈의 전역 이름을 덮어쓰지 않는다.
- **입력 경계**: 입력을 소비하는 Step은 구간 반복자에서 종료를 받는다. 구버전이 지연 출력을 모두 낸 뒤 새 버전에 남은 원본 입력을 연결한다.
- **소스 경계**: 첫 Step은 입력을 소비하지 않으므로 출력 다음 경계에서 이전 생성기를 닫고 새 버전을 시작한다. 수신 중 블로킹 호출은 해당 호출이 끝날 때까지 즉시 교체되지 않는다.
- **상태 경계**: 래퍼가 출력에 내부 세대 식별자를 붙인다. 하류 래퍼는 변경된 첫 입력을 보관하고 이전 구간을 마무리한 뒤 새 구간에서 그 입력을 한 번 처리한다.
- **인스턴스 상태**: 코드 변경 시 이전 인스턴스의 속성을 새 클래스 인스턴스로 옮긴다. 상류 변경으로 재시작할 때는 생성자 인자명과 같은 이전 속성을 찾아 생성자를 다시 호출한다. 복원할 수 없는 인자는 속성 복사로 처리하므로 이 경우 자체 상태가 남을 수 있다.
- **제한**: 네트워크 재연결만으로는 소스 코드가 바뀐 것이 아니므로 세대 경계가 발생하지 않는다. 실제 GPU·RTSP 동작은 별도 환경에서 확인해야 한다.
# 추가 조사: 별도 프로세스의 사용자 Step

- 결정: 등록 시 보존한 파일 경로를 변경 감지의 기준으로 유지한다.
- 근거: 전달된 `__main__` 클래스의 모듈 정보는 실행 프로세스의 정보와 달라질 수 있다.
- 결정: 새 파일을 실행하는 동안 원본 파일의 패키지 루트를 일시적으로 모듈 검색 경로에 넣고, 가져오기 잠금 아래에서 항상 복원한다.
- 근거: 예제의 메인 파일은 같은 디렉터리의 `step` 패키지를 가져오지만 중앙 프로세스의 시작 경로에는 그 디렉터리가 없을 수 있다.
- 고려한 대안: 중앙 프로세스의 검색 경로에 예제 디렉터리를 영구 추가하는 방법은 다른 파이프라인의 모듈 해석에 영향을 주므로 채택하지 않는다.
