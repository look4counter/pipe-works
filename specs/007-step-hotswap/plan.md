# 구현 계획: 실행 중 Step 구현 교체

**명세**: [기능 명세](spec.md)

## 기술 배경

- `Pipeline.step()`은 현재 원래 Step을 설정한 뒤 목록에 등록한다.
- 각 Step은 `process(inputs)` 생성기를 통해 흐름 전체를 처리한다.
- `RTSPSource`는 입력을 소비하지 않는 무한 소스이고, `RTSPPublish`는 출력을 만들지 않는 소비 단계다.
- `NvidiaEncode`는 입력 종료 때 `EndEncode()`를 호출한다. `NvidiaDecode`에는 종료 시 `Flush()`가 없다.
- 프로젝트 헌장은 채워지지 않은 템플릿이다. 저장소의 소스 변경 절차를 적용한다.

## 설계

1. `Pipeline.step()`에서 원래 클래스명으로 YAML 섹션을 선택한다. 내장 Step은 직접 설정해 등록하고, 사용자 Step은 `Hotswap`으로 감싸 설정한다. 이미 감싼 인스턴스는 중복 포장하지 않는다.
2. `Hotswap`은 원래 Step의 모듈 파일을 제한된 간격으로 검사한다. 내용이 바뀌면 별도 모듈 이름으로 코드를 실행해 같은 이름의 새 클래스를 준비한다. 준비에 실패하면 기존 Step을 유지한다.
3. 새 인스턴스는 이전 인스턴스의 속성 사전을 복사해 설정과 생성자에서 보관한 값을 이어받는다. 새 구현의 `process()`는 기존 입력 반복자와 분리된 새 실행 구간에서 시작한다.
4. 입력 소비 Step에는 구간별 입력 반복자를 전달한다. 파일 변경이나 상류 세대 변경을 감지하면 다음 입력 요청에서 구간 종료를 알리고, 이전 `process()`가 남은 출력을 모두 내도록 소비한다. 경계에서 읽은 첫 입력은 다음 구간에 보관했다가 정확히 한 번 전달한다.
5. 첫 소스 Step은 입력 경계를 읽지 않으므로 출력 경계에서 기존 생성기를 닫고 새 생성기를 시작한다.
6. 래퍼는 출력 컨텍스트에 내부 세대 식별자를 붙인다. 상류 세대가 달라지면 하류 래퍼도 이전 구간을 마무리하고 같은 클래스의 새 실행 구간을 만든다. 생성자 인자는 같은 이름의 기존 인스턴스 속성에서 복원하며, 복원할 수 없으면 속성 복사로 전환한다. 인코더의 잔여 패킷은 이전 세대에 속한다.
7. 디코더 입력 종료 후 `Flush()` 결과를 같은 프레임 계약으로 전달한다.
8. 파일 검사는 단조 시계 간격으로 제한하며, 처리 중 파일 내용을 매번 읽지 않는다.
9. `Hotswap.configure()`가 설정 객체를 보관하고 내부 Step에 전달한다. 새 Step을 만들 때 이전 Step의 `config`를 조회하지 않고 보관한 설정으로 다시 구성한다. `Pipeline.step()`은 래퍼의 `configure()`를 호출한다. 기본 Step의 `configure()`는 공통 상태를 저장하지 않고, 내장 단계는 필요한 값을 개별 속성에만 기록한다.
10. 클래스 정의 파일이 `src/pipeworks/embedded` 아래인지 검사하는 공통 함수를 둔다. `Pipeline.step()`과 `Tap`가 자동 포장 여부를 판단할 때 사용한다. 명시적 `Hotswap`은 그대로 등록한다.

내장 Step이 원본 입력을 새 컨텍스트로 바꾸는 경우 교체 세대가 전달되지 않을 수 있다. 자동 교체 세대 전파는 연속한 래퍼 구간에 한정한다.

## 사용자 Step 오류 복구

1. 구간 입력 반복자가 사용자 Step에 넘긴 원래 컨텍스트와 최상위 속성 사본을 마지막 출력 이후부터 기록한다. 정상 출력이 나오면 기록을 비운다.
2. `process()` 생성·반복·정리 중 오류를 잡아 로그를 남기고 기록된 컨텍스트의 속성을 복원한 뒤 순서대로 출력한다. 상류 반복자의 오류는 별도로 표시해 다시 발생시킨다.
3. 오류가 난 처리 반복자를 정리하고 같은 클래스의 Step을 다시 구성해 남은 입력에 연결한다. 재구성 오류가 있으면 기존 인스턴스로 다음 처리 구간을 시도한다.
4. 사용자 정의 소스 Step 오류에는 반환할 입력이 없으므로 오류를 기록하고 짧은 대기 후 재시도한다.

## 별도 프로세스의 사용자 Step 파일 교체

1. 기존 `Hotswap` 인스턴스에 보존된 원본 파일 경로와 패키지명을 사용한다. 직렬화 후 클래스의 `__main__` 정보로 경로를 다시 추론하지 않는다.
2. 변경 파일을 실행하는 짧은 구간에서 원본 파일의 패키지 루트를 모듈 검색 경로에 추가한다. 패키지명이 없으면 파일의 부모 디렉터리를 사용한다. 성공과 실패 모두 검색 경로를 복원한다.
3. 파일 준비 구간을 잠금으로 직렬화하고 파이썬 가져오기 잠금도 유지해 다른 스레드의 모듈 로딩과 경로 변경이 겹치지 않도록 한다. 저장 중 파일 오류에서는 기존 구현을 계속 사용한다.
4. 실행 파일에 정의된 `PostProcess`와 예제 디렉터리의 사용자 Step에 대해 중앙 프로세스 전달 후 파일 변경을 검증한다.

## 검증

- 임시 모듈의 처리 로직을 실행 중 수정하고 출력 순서를 확인한다.
- 입력을 미리 읽는 Step, 출력을 만들지 않는 Step, 입력이 없는 소스 Step을 각각 모의한다.
- 잘못된 변경 파일에서 이전 구현이 계속 동작하는지 확인한다.
- 상류 변경 후 하류 재시작과 경계 입력의 단일 처리를 확인한다.
- 전체 단위 테스트와 구문·문서 참조 검사를 수행한다.
- 사용자 모듈이 평소 모듈 검색 경로에 없는 상태에서 교체를 검증하고, 검사 뒤 검색 경로가 복원되는지 확인한다.
