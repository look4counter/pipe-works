# 기능 명세: 실행 중 Step 구현 교체

**작성일**: 2026-10-03
**상태**: 구현 대상

## 사용자 시나리오와 검증

### 시나리오 1: 기존 Step 코드 수정 반영

사용자는 영상 처리가 진행되는 동안 사용자 정의 Step의 소스 파일을 수정한다. 파이프라인은 프로세스를 종료하지 않고 새 구현을 적용한다.

**인수 조건**:

1. 사용자는 기존 `.step(단계 인스턴스)` 체인을 그대로 사용한다.
2. 변경하지 않은 파일은 반복 처리 중 다시 읽거나 Step을 재생성하지 않는다.
3. 소스 파일 변경을 확인하면 기존 Step에 더 이상 새 입력을 주지 않고, 기존 Step이 그동안 받은 입력의 출력을 모두 내도록 기다린다.
4. 기존 출력이 끝난 뒤 새 구현으로 남은 입력을 처리한다.
5. 새 파일을 읽거나 실행할 수 없으면 기존 구현을 유지하고 처리를 계속한다.
6. 실행 파일과 예제 디렉터리에 정의된 사용자 Step도 별도 실행 프로세스에서 원본 파일의 변경을 감지하고 교체한다.

### 시나리오 2: 상태 있는 영상 단계의 경계 유지

명시적으로 `Hotswap`으로 감싼 수신·디코딩·인코딩·송출 단계 중 하나가 교체되더라도, 이어지는 단계는 이전 흐름을 마무리하고 새 흐름으로 전환한다.

**인수 조건**:

1. 소스 변경 시 기존 RTSP 연결을 닫고 새 구현으로 다시 연결한다.
2. 디코더는 입력 종료 때 내부에 남은 프레임을 전달한다.
3. 인코더는 입력 종료 때 잔여 패킷을 전달한다.
4. 상류 단계가 새 흐름으로 넘어가면 하류 단계는 이전 입력에서 나온 출력을 마친 뒤 내부 상태를 새로 시작한다.
5. Step 추가·삭제·순서 변경은 실행 중 자동 반영 범위에 포함하지 않는다.

### 시나리오 3: 사용자 정의 Step 오류 후 프레임 전달

사용자 정의 Step의 `process()` 실행 중 오류가 발생하면 앱은 계속 실행되고, 마지막 정상 출력 이후 해당 Step이 받은 원래 입력 프레임을 다음 Step으로 전달한다. 이후 입력은 다시 시작한 Step이 처리한다.

**인수 조건**:

1. 오류를 기록하고 해당 입력 컨텍스트 객체와 프레임을 바꾸지 않고 출력한다.
2. 하나 이상의 입력을 보관하다 실패한 Step은 마지막 정상 출력 이후 받은 입력을 원래 순서대로 출력한다.
3. 다음 프레임에서도 같은 Step의 처리를 시도한다.
4. 내장 Step이나 상류 Step의 오류를 사용자 Step 오류로 오인하지 않는다.
5. 소스 Step에는 되돌릴 입력 프레임이 없으므로 오류를 기록한 뒤 재시도한다.

## 기능 요구사항

- **FR-001**: `Pipeline.step()`은 설정 섹션을 원래 Step의 클래스명으로 조회하고, `src/pipeworks/embedded`에 정의되지 않은 Step만 자동으로 교체 래퍼로 감싸야 한다.
- **FR-002**: 래퍼는 기존 `Step.process(inputs)` 반복자 계약을 유지해야 한다.
- **FR-003**: 래퍼는 Step 소스 파일의 내용 변경을 실행 중 확인하고, 새 구현을 이전 실행과 분리해 준비해야 한다.
- **FR-004**: 변경된 구현을 준비하지 못하면 현재 구현을 계속 사용해야 한다.
- **FR-005**: 입력을 소비하는 Step은 교체 시 입력 경계를 전달받고 잔여 출력을 완료한 뒤 새 구현으로 이어야 한다.
- **FR-006**: 입력을 소비하지 않는 첫 소스 Step은 출력 경계에서 이전 생성기를 정리하고 새 구현을 시작해야 한다.
- **FR-007**: 연속해서 교체 래퍼로 감싼 단계에서는 상류 구현 교체를 하류 Step의 상태 재시작으로 전파해야 하며, 경계에 걸린 입력을 잃지 않아야 한다.
- **FR-008**: 디코더는 정상 입력 종료와 교체 경계에서 지연 프레임을 회수해야 한다.
- **FR-009**: 파일 확인은 프레임마다 파일 내용을 읽지 않도록 제한해야 한다.
- **FR-010**: 교체 래퍼는 등록 시 받은 설정 객체를 단계 인스턴스와 별도로 보관하고, 코드 교체 및 상류 변경에 따른 재시작 때 새 단계의 `configure()`에 다시 전달해야 한다. 단계는 공통 `self.config` 속성에 의존하지 않아야 한다.
- **FR-011**: `Tap`의 내부 Step에도 동일한 자동 제외 규칙을 적용해야 한다. 명시적으로 전달된 `Hotswap`은 유지해야 한다.
- **FR-012**: 사용자 정의 Step의 `process()`가 예외를 내면 래퍼가 기록하고 마지막 정상 출력 이후 소비한 입력 컨텍스트의 최상위 속성을 복원해 원래 순서대로 전달해야 한다.
- **FR-013**: 런타임 오류 후 Step 처리 반복자를 다시 시작하고 후속 입력을 계속 처리해야 한다. 사용자 정의 소스 Step의 오류는 기록하고 재시도해야 한다.
- **FR-014**: 상류 또는 내장 Step에서 발생한 예외는 사용자 Step 오류로 처리하지 않아야 한다.
- **FR-015**: 별도 프로세스에서 실행되는 사용자 Step은 등록 당시 확인한 원본 파일을 계속 감시하고, 그 파일에서 사용하는 같은 디렉터리의 사용자 모듈을 새 구현 준비 때도 읽을 수 있어야 한다.
- **FR-016**: 사용자 Step 교체를 위한 파일 준비 중 임시로 필요한 모듈 검색 경로는 다른 파이프라인의 실행과 충돌하지 않도록 관리해야 한다.

## 성공 기준

- **SC-001**: 모의 입력 흐름 중 Step 파일을 수정하면 기존 구현의 출력 다음부터 새 구현의 출력이 나온다.
- **SC-002**: 버퍼링 Step의 이전 입력에 대한 잔여 출력이 새 구현 출력보다 먼저 나온다.
- **SC-003**: 잘못된 새 파일을 저장해도 기존 구현의 출력이 계속된다.
- **SC-004**: 연속해서 교체 래퍼로 감싼 단계에서 상류 교체 시 하류 Step이 재생성되고 경계의 첫 입력이 정확히 한 번 처리된다.
- **SC-005**: 기존 테스트가 모두 통과하고 `.step(...)` 예제 형태가 유지된다.
- **SC-006**: 설정을 개별 속성에만 저장하는 단계가 코드 교체와 상류 재시작 후에도 같은 설정으로 동작한다.
- **SC-007**: 내장 Step은 `Pipeline`과 `Tap`에서 자동으로 감싸지지 않고, 사용자 Step은 계속 감싸지며 설정과 실행 결과가 유지된다.
- **SC-008**: 사용자 Step이 한 프레임에서 실패해도 앱이 계속 실행되며 해당 프레임 객체가 한 번 출력되고 다음 프레임 처리가 성공한다.
- **SC-009**: 사용자 Step이 여러 프레임을 소비한 뒤 실패해도 마지막 출력 이후의 원본 입력이 원래 순서대로 전달된다.
- **SC-010**: `01_single_stream_rtsp_style.py`와 같은 구조의 메인 파일 및 같은 예제 디렉터리의 Step을 별도 프로세스에서 실행한 뒤 각각의 파일을 수정하면, 다음 처리 경계부터 새 동작이 나타난다.

## 범위와 가정

- Step의 파일과 클래스 이름은 유지하며, 생성자와 `configure()`가 관리하는 인스턴스 속성 형태는 호환된다고 가정한다.
- 래퍼는 기존 인스턴스의 속성을 새 클래스 인스턴스에 이전한다. 생성자 자체의 새 부작용이나 외부 자원 이전은 보장하지 않는다.
- 상류 변경으로 Step을 다시 시작할 때 생성자 인자와 같은 이름의 속성이 있으면 생성자를 재호출한다. 인자를 복원할 수 없는 Step은 속성 복사로 이어가므로 자체 상태 초기화를 보장하지 않는다.
- 소스 변경은 다음 출력 경계에서 적용된다. 수신 호출이 끝나지 않으면 즉시 전환할 수 없다.
- Step은 유한한 입력 구간의 끝을 받으면 잔여 출력을 내고 종료해야 한다. 종료하지 않는 사용자 Step의 교체는 완료될 수 없다.
- 동일한 파일의 여러 변경이 짧게 연속되면 가장 최근에 정상적으로 준비된 구현을 적용한다.
- 자동 교체에서 제외한 내장 Step이 중간에 있으면 해당 구간을 가로지르는 교체 세대 전파는 보장하지 않는다.
- 일반 반복자 Step의 출력과 입력은 일대일 대응이 아닐 수 있다. 오류 시 마지막 정상 출력 이후 받은 입력을 되돌리는 규칙을 적용하며, 이미 출력이 발생한 이전 입력은 다시 전달하지 않는다.
- `configure()`나 생성자 오류는 프레임 입력 이전에 발생하므로 이 복구 범위에 포함하지 않는다.
- 컨텍스트 속성은 얕게 보관하므로 Step이 프레임 메모리나 중첩 객체의 내부 값을 직접 변경한 경우까지 복원하지는 않는다.

## 명확화 결과

- 등록 문법은 별도 `fixed_step`·`hot_step` 없이 `.step(...)` 하나를 사용한다.
- 사용자 Step을 자동으로 감싸되, 내장 Step은 제외한다. 메인 파일의 Step 목록 변경은 재시작 대상이다.
- 입력을 소비하는 Step에는 유한한 입력 구간의 종료를 전달하고 잔여 출력을 끝까지 소비한다. 첫 소스 Step에는 출력 경계에서 정리를 요청한다.
