# 기능 명세: 중앙 프로세스 구조화 로그 중계

**작성일**: 2026-10-15
**상태**: 검증 완료
**입력**: 구조화 로그 중계를 기본으로 전환하고 기존 print 전달은 DEBUG 호환 어댑터로 유지한다.

## 사용자 시나리오와 검증

### 사용자 이야기 1 — 호출자의 로깅 정책 적용 (우선순위: P1)

운영자는 중앙 실행에서도 로컬과 같이 모듈별 레벨과 콘솔·파일 핸들러로 로그를 제어한다.
**우선순위 이유**: 중앙 실행의 출력 경로를 표준 로깅으로 바꾸는 핵심이다.
**독립 검증**: 중앙에서 여러 수준의 로그와 예외를 발생시키고 호출자의 핸들러에 원래 이름·수준·시각·발생 위치·예외 정보가 전달되는지 검증한다.

1. 호출자가 DEBUG를 허용하면 중앙의 DEBUG 보고를 받고 INFO 이상만 허용하면 숨긴다.
2. 모듈별 로그 수준과 핸들러 수준·필터를 적용한다.
3. 한 로그가 한 번만 전달되며 파이프라인 실패 응답도 기존대로 전달된다.

### 사용자 이야기 2 — 동시 실행과 비동기 작업자 분리 (우선순위: P1)

동시에 실행하는 파이프라인은 자신의 로그와 자신의 레벨 정책만 적용받는다.
**독립 검증**: 서로 다른 정책으로 동시 요청을 보내고 비동기 Step·보고 스레드의 로그 및 오류가 각 호출자에게만 도착하는지 검증한다.

1. 로그에는 파이프라인 이름과 고유 실행 식별자가 포함된다.
2. 기존 라이브러리 작업자의 로그 및 정리 시 로그가 실행 문맥을 따른다.
3. 연결이 끊기면 해당 실행을 중지하고 로그 전송 실패를 재귀적으로 기록하지 않는다.

### 사용자 이야기 3 — 기존 사용자 print 호환 (우선순위: P2)

기존 사용자 Step의 print를 수정하지 않아도 DEBUG 수준에서 메시지를 확인한다.
**독립 검증**: 분할 쓰기·다중 인자·줄바꿈·flush·마지막 부분 줄을 중앙 실행하여 기록 순서와 중복 여부를 확인한다.

1. print와 stdout.write는 줄 단위 DEBUG 기록으로 변환되고 호출자의 로깅 설정에 따라 출력된다.
2. 정상 종료와 오류 응답 전까지 남은 부분 줄을 기록한다.
3. 기존 로컬 실행의 print와 로깅 정책은 변경하지 않는다.

### 경계 조건

- Python stdout 호환이며 네이티브 라이브러리의 파일 디스크립터 직접 출력과 stderr 가로채기는 포함하지 않는다.
- 사용자가 새로 만든 스레드는 기존처럼 라이브러리 실행 문맥 전달에 참여해야 한다. 문맥 없는 로그를 임의의 파이프라인으로 보내지 않는다.
- 완료된 실행의 늦은 비동기 로그는 다른 실행에 섞이지 않도록 버린다.
- 직렬화할 수 없는 로그 인자·추가 값이 있어도 메시지와 오류 응답 중계가 중단되지 않는다.
- 무개행 출력 버퍼는 스레드별 최대 64KiB로 제한하고 긴 줄은 여러 DEBUG 기록으로 나눈다.

## 요구사항

- **FR-001**: IPC에 문자열 출력 대신 구조화 로그를 전송하고 수신 로거의 핸들러로 처리한다. 이름·수준·메시지·발생 시각·소스 위치·프로세스/스레드·예외 문자열 및 실행 정보를 유지한다.
- **FR-002**: 요청 시작 시 호출자의 루트 및 이름별 수준·비활성 상태·전역 비활성 기준을 전달한다. 서버는 실행별 정책으로 필터하고 호출자는 수신 시 현재 로거·핸들러 설정을 적용한다. 서버에서 요청마다 전역 수준을 높였다 낮추지 않는다.
- **FR-003**: 실행별 문맥과 고유 ID로 동시 호출의 로그 및 print를 격리하고 라이브러리 작업자에 전파한다. 중첩 범위 종료 시 이전 문맥을 복원한다.
- **FR-004**: 기존 stdout 출력 캡처를 줄 단위 DEBUG 로깅 어댑터로 유지한다. flush·마지막 부분 줄·분할 쓰기·64KiB 상한을 처리한다.
- **FR-005**: 전송 실패 시 실행을 중지하고 무재귀로 처리한다. 마지막 로그는 완료 응답 전에 보내며 종료된 실행의 로그는 폐기한다.
- **FR-006**: 통신 버전을 올려 기존 중앙 프로세스와 새 메시지 형식이 혼용되지 않게 한다. 기존 사용자 Step 직렬화·하트비트·실패 응답·유휴 종료·프로세스 그룹·로컬 실행 동작을 유지한다.
- **FR-007**: 중앙에서 준비된 로거의 명시 수준·비전파 및 기존 핸들러가 로그 중계를 차단하거나 중복 출력하지 않게 한다. 사용자 핸들러는 호출자에서 적용한다.

## 성공 기준

- **SC-001**: 실제 별도 프로세스 시험에서 DEBUG/INFO/예외와 모듈별 정책 및 파일/메모리 핸들러가 기대대로 동작하고 로그가 중복되지 않는다.
- **SC-002**: 서로 다른 수준의 동시 요청과 비동기 Step의 로그가 다른 호출자에게 전달되는 경우가 0건이다.
- **SC-003**: 호환 print의 분할·flush·부분 줄 시험을 통과하고 INFO 정책에서 DEBUG 출력은 0건이다.
- **SC-004**: 기존 중앙 실행·비동기·보고·실행 경로 회귀 시험을 통과한다.

## 주요 개체

- 실행 요청: 파이프라인, 고유 실행 ID, 호출자 로그 정책.
- 실행 경로: 전송 함수, 정책, 실행 이름/ID, 활성 상태.
- 로그 패킷: 렌더된 표준 로그 필드와 안전하게 변환한 추가 필드.
- stdout 어댑터: 실행별·스레드별 부분 줄 버퍼.

## 가정과 명확화

추천 방식이 승인되어 추가 질문이 필요한 모호성은 없다. print는 pipeworks.user_output 로거의 DEBUG로 바뀌므로 기본 WARNING 설정에서는 숨겨진다. 서버에서 실행 도중 로거 수준을 새로 제한하면 생성 전 필터링될 수 있으므로 로그 정책은 호출자에서 설정한다. 실행 중 호출자 수준을 낮추어도 이미 송신 단계에서 필터된 로그를 복원하지는 않는다.
