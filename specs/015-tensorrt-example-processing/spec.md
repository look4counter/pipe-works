# TensorRT 예제 전처리·후처리 명세

## 사용자 시나리오 8: 표시·후처리 설정을 예제 클래스에서 관리 (우선순위 P1)

개발자는 BoxOverlay와 TensorRTPostProcess의 설정을 예제 클래스 내부에서 관리한다. 제공 YAML에서 두 섹션을 삭제해도 기존 표시와 클래스 2 탐지 동작을 유지한다.

수용 시나리오:

1. BoxOverlay는 별도 설정 없이 모든 모델 결과를 초록색 두께 2로 표시하고 이전 결과를 유지한다.
2. TensorRTPostProcess는 별도 설정 없이 클래스 [2]·신뢰도 0.25·IoU 0.7·최대 탐지 300·출력 output0을 사용한다.
3. 제공 YAML의 다른 설정과 기존 GPU 처리·좌표 복원·ID별 결과·비동기 수명 계약은 보존한다.

- FR-028: examples/config/stream.yml에서 BoxOverlay와 TensorRTPostProcess 섹션을 제거한다. 다른 섹션의 사용자 설정은 보존한다.
- FR-029: 두 클래스의 내부 기본값으로 기존 제공 YAML 값을 보관하고 직접 생성 및 파이프라인의 빈 구성 적용 시 같은 값으로 동작한다. 구성 검증·명시적 configure 덮어쓰기 기능은 유지하고 빈 구성은 내부 기본값으로 복원한다. 후처리의 classes 목록은 인스턴스별 독립 저장 공간을 사용한다.
- FR-030: 현재 문서와 테스트는 YAML 없는 기본 동작을 안내·검증한다. GPU 처리와 탐지 필터·NMS·좌표 복원·표시·ID 선택·정리 동작은 유지한다.
- SC-013: 제공 YAML의 두 설정 섹션이 0개이고 YAML 없이 기존 예제가 같은 설정으로 구성된다. 기본 클래스 필터와 표시 설정, 구성 복원·목록 격리와 관련 기존 회귀가 통과한다.

명확화: 이전 전처리 이동 요청과 같은 방식으로 제공 YAML의 설정을 클래스 내부 기본값으로 옮긴다. configure API 자체의 제거는 요청하지 않았으므로 유지한다. 별도 질문이 필요한 모호성은 없다. 과거 예제 YAML 노출 요구는 이번 섹션 제거로 대체한다.

## 사용자 시나리오 7: 전처리를 사용자 예제로 분리 (2026-10-11, 우선순위 P1)

개발자는 모델별 전처리를 예제 코드에서 직접 관리하고 내장 실행 단계와 구분한다. 기존 예제는 전처리 설정 섹션 없이 같은 입력과 탐지 결과를 만든다.

수용 시나리오:

1. 예제 경로의 전처리 클래스를 사용하면 기존 픽셀 변환·좌표 복원 정보·CUDA 스트림·프레임 수명·성능 보고가 유지된다.
2. 내장 패키지에는 전처리 클래스와 모듈이 없으며 예제·검증·도구는 새 경로를 사용한다.
3. 제공 YAML에서 전처리 섹션을 제거해도 생성자 기본값으로 기존 예제를 구성할 수 있고 다른 설정은 보존된다.

- FR-025: TensorRTPreProcess 구현을 examples/step/tensor_rt_pre_process.py에서 제공하고 내장 모듈과 내보내기를 제거한다. 내장 경로의 호환 모듈은 남기지 않는다.
- FR-026: 기존 생성자 옵션·구성 검증·GPU 처리와 입출력·좌표 변환·스트림·프레임 해제·보고 계약을 유지한다. 예제·테스트·도구·현재 사용 안내는 예제 경로를 사용한다.
- FR-027: examples/config/stream.yml의 TensorRTPreProcess 섹션과 관련 주석을 제거한다. 다른 섹션의 사용자 변경은 보존하며 예제는 생성자 기본값으로 동작한다.
- SC-012: 제공 예제의 내장 전처리 의존성과 제공 YAML의 전처리 설정이 각각 0개다. 전처리·좌표 복원·후처리·보고·모델 ID의 기존 검증에 이번 변경으로 발생한 실패가 없다.

명확화: 사용자 요청은 구현 위치와 제공 YAML 변경이다. 알고리즘 단순화나 생성자·configure의 설정 기능 제거를 요청하지 않았으므로 유지한다. 모든 현재 참조를 이동하고 과거 검증 기록은 이력을 보존한다. 추가 질문이 필요한 모호성은 없다. 이번 요구사항이 과거 내장 공개 경로·전체 옵션 YAML 노출 요구를 대체한다.

## 사용자 시나리오 6: YOLO와 TensorRT의 공통 모델 ID (2026-10-11, 우선순위 P1)

같은 YOLO 모델을 직렬로 사용하는 개발자는 실행 단계별 ID로 결과를 보관하고 TensorRT 결과와 같은 사전에서 선택한다.

- FR-022: YoloDetect는 선택적 id 생성자·YAML 설정을 제공한다. 생략/null은 확장자 포함 모델 파일명이며 지정 값은 공백뿐인 값이 아닌 문자열이다. YAML 우선·제거 시 최초 생성자 값 복원·검증 실패 시 기존 구성 보존을 적용한다.
- FR-023: 개별·배치·간격 건너뜀 모두 detections[id]에 결과 또는 None을 저장한다. 같은 ID만 교체하고 다른 YOLO/TensorRT 결과는 유지한다. 결과 사전은 복사하여 비동기 원본 컨텍스트의 공유 사전을 수정하지 않는다. 입력 경계에서 ID를 고정한다.
- FR-024: 기존 개별 모드 오류 전파와 배치 모드 오류 로그·통과를 유지하며 오류 시 현재 ID만 None이다. 원본 프레임·GPU 수치·스트림·해제 신호·모델/배치 공유·성능 보고는 유지한다. 기존 단일 결과 객체를 자동으로 ID에 배정하지 않고 잘못된 결과 저장 형식은 명확히 거부한다.
- SC-011: ID 구성·YAML 복원·동일 모델 직렬 결과·동일 ID 교체·다른 결과 보존·개별/배치/건너뜀/오류·비동기 격리·실행 중 ID 변경·Overlay 소비 검증과 기존 YOLO 회귀가 통과한다.

명확화: 이전 TensorRT 작업에서 제외했던 YOLO 결과 저장 형식을 이번 요청으로 동일하게 변경한다. YoloDetect는 후처리까지 내부에서 완료하므로 임시 model_id 속성을 추가하지 않고 결과 사전에 직접 저장한다. local_yolo.infer의 직접 반환값은 기존 결과 객체를 유지한다. 별도 질문은 필요하지 않다.

## 사용자 시나리오 5: 직렬 모델 결과 식별 (2026-10-11, 우선순위 P1)

같은 모델 파일을 직렬로 실행하는 개발자는 각 단계에 ID를 지정하여 결과를 따로 보관하고 마지막 Overlay에서 전체 또는 원하는 결과만 표시한다.

- FR-018: TensorRTInference는 선택적 id 생성자·YAML 설정을 지원한다. 생략 또는 null이면 확장자를 포함한 모델 파일명이고 지정 값은 공백뿐인 값이 아닌 문자열이다. YAML 제거 시 최초 생성자 값으로 돌아간다. 개별·배치·건너뛴 입력 모두 model_id로 전달한다.
- FR-019: TensorRT 탐지 결과는 detections의 ID별 사전에 저장한다. 같은 ID는 교체하며 다른 ID는 보존한다. 출력 누락·오류는 해당 ID만 None으로 처리하고 전처리는 기존 결과를 초기화하지 않는다. 비동기 작업이 공유 사전을 제자리 수정하지 않는다.
- FR-020: BoxOverlay의 선택적 id 설정은 해당 결과만 표시하고 생략 시 전체를 표시한다. keep_previous는 ID별로 적용하고 빈 탐지는 해당 ID의 이전 박스를 지운다. 기존 YOLO 단일 결과 표시도 유지한다.
- FR-021: 후처리 완료·누락·오류에서 임시 model_id도 정리하며 기존 CUDA 스트림·프레임 보존·버퍼 수명·프로파일링을 유지한다.
- SC-010: ID 기본값·명시값·잘못된 값·YAML 복원·개별/배치/간격 전달, 실제 같은 엔진의 직렬 실행·다른 ID 보존·동일 ID 교체·건너뜀·Overlay 선택·ID별 이전 결과·비동기 결과 격리 검증이 통과한다.

수용 시나리오: vehicle·person ID의 같은 엔진 실행 결과를 모두 보관하고 두 추론을 마친 뒤 박스를 표시한다. 같은 ID 재실행은 이전 결과만 교체한다. 한 모델이 건너뛰면 다른 모델의 현재 결과를 유지한다.

명확화: Overlay 선택 설정명도 id이고 null은 전체다. 결과가 없는 ID는 None으로 저장한다. 이전 YOLO 결과 객체는 Overlay에서 호환 처리하며 현재 YOLO 저장 형식은 후속 FR-022~024를 따른다. 보고 단계는 성능 통계를 읽고 DB 예제는 저장 미구현이므로 새 저장 기능을 추가하지 않는다. 원본 픽셀을 수정하는 Overlay는 모든 추론 뒤에 둔다. 추가 질문은 필요하지 않다.

- FR-017: 전처리 파일명은 tensor_rt_pre_process.py를 유지하며 후속 FR-025의 예제 위치로 이동한다. 현재 소스·예제·테스트·도구의 import와 패치 경로를 갱신하고 클래스명과 처리 동작은 유지한다.

명확화: 사용자 지정 파일명으로 직접 이동한다. 옛 내장 모듈 호환 파일은 추가하지 않는다. 문서 파일명과 테스트 파일명은 유지하며 코드 경로 문서만 갱신한다. 별도 질문은 필요하지 않다.

## 요구사항

- FR-001: TensorRTPreProcess는 원본 영상을 읽기 전용으로 유지하고 기본 설정에서 GPU NV12를 FP32 RGB 1×3×640×640으로 변환한다. 비율을 유지하고 중앙 패딩을 넣으며 원본 크기·비율·패딩을 보관한다. 범용 설정은 후속 FR-007~012를 따른다.
- FR-002: TensorRTPostProcess는 output0의 1×84×8400 YOLO 출력을 해석하고 신뢰도·클래스 필터와 클래스별 NMS를 적용한 뒤 원본 좌표를 복원한다. 감지 객체에 좌표·신뢰도·클래스 ID와 COCO 이름을 제공한다. 결과 저장과 누락 처리는 FR-019의 ID별 사전 계약을 따른다.
- FR-003: 두 단계는 클래스명 YAML 설정과 Hotswap을 지원하며 GPU 텐서를 CPU로 복사하지 않는다. 형식·설정 오류는 명확히 거부한다.
- FR-004: 단일 예제는 실제 plan 경로와 올바른 클래스명을 사용한다. 일반 TensorRTInference에 batch 인자는 전달하지 않는다.

## 성공 기준

- SC-001: 실제 엔진 입력·출력 형식, 원본 입력 보존·패딩·정규화와 좌표 복원·필터·NMS·빈 결과 검증이 통과한다.
- SC-002: 예제 생성과 기존 감지 결과 소비 검증이 통과한다.

## 명확화

추가 질문이 필요한 모호성은 없다. 제공된 plan을 직접 검사했으며 입력 images FP32 1×3×640×640, 출력 output0 FP32 1×84×8400이다. 후처리는 COCO YOLO11 탐지 엔진 예제로 제한한다. 전처리는 후속 요청에 따라 다양한 이미지 모델의 입력 규칙을 지원한다. 기본 신뢰도 0.25·IoU 0.7·최대 감지 300, 클래스 필터 [2]는 예제 기존 설정을 유지한다.
## CUDA 스트림 분리·버퍼 정리

- FR-005: 전처리·직접 추론·후처리는 컨텍스트 cuda_stream에서 실행한다. 공유 배치는 입력 준비 이벤트를 내부 작업자 스트림에서 기다린다. 기존 cuda_stream 객체는 보존한다.
- FR-006: 후처리 성공·누락·실패 시 model_input·model_output·복원 정보·모델 스트림 참조를 정리한다. 감지 결과와 원본 영상은 보존하고 GPU 완료 전에 저장 공간을 해제하지 않는다.
- SC-003: 실제 CUDA의 스트림 분리·영상 보존·결과 준비·버퍼 정리·실제 엔진과 Async 회귀가 통과한다.

명확화: 최신 요청은 전후처리의 영상 스트림 사용을 대체한다. 모델 작업 완료를 호스트에서 확인하여 공통 Async의 안전한 입력 수명 계약을 유지한다. 강제 메모리 캐시 비우기나 복수 Async 신호 최적화는 범위에 포함하지 않는다. 추가 질문은 필요하지 않다.

## 후속 사용자 시나리오: 범용 GPU 이미지 전처리 (2026-10-10)

### 사용자 시나리오 1: 모델별 입력 규칙 선택 (우선순위 P1)

개발자는 예제 TensorRTPreProcess의 설정을 바꿔 탐지·분류 등 서로 다른 이미지 모델에 맞는 입력을 준비한다. 특정 모델 공급자의 라이브러리를 사용하지 않고 GPU에서 변환한다.

독립 검증: 같은 합성 이미지에 letterbox, stretch, 중앙 자르기와 서로 다른 색상·정규화·출력 형식을 적용해 크기와 픽셀 값을 확인한다.

수용 시나리오:

1. 기존 기본 설정은 같은 크기·RGB 순서·정규화·원본 보존과 후처리 복원 정보를 유지한다.
2. 이름을 지정한 이미지 입력은 그 이름의 사전으로 전달되고 추가 입력은 다른 단계가 조합할 수 있다.
3. YAML의 일부 설정을 덮어쓰고 제거하면 최초 생성자 설정으로 돌아간다.
4. 잘못된 설정은 GPU 작업 전에 명확한 오류로 거부한다.

### 사용자 시나리오 2: 기존 파이프라인에서 안전하게 사용 (우선순위 P2)

기존 예제를 내장 전처리로 연결하고 비동기 실행·원본 프레임 수명·별도 모델 스트림·감지 보고를 유지한다.

독립 검증: 기존 전후처리·비동기 수명·보고 검증과 실제 예제 엔진을 실행한다.

### 기능 요구사항

- FR-007: 전처리 공개 위치는 후속 FR-025의 예제 경로를 따른다. 기존 내장 경로 공개 요구는 대체한다.
- FR-008: size, resize_mode, auto, stride, scaleup, center, padding_value, crop_size로 크기 변경을 설정한다. letterbox는 비율 유지·패딩, stretch는 지정 크기로 늘리기, resize_center_crop은 비율 유지 리사이즈 후 중앙 자르기를 수행한다.
- FR-009: color_order, scale, mean, std, dtype, layout으로 채널 순서·정규화·출력 형식을 설정한다. 정규화는 (원본 픽셀 × scale − mean) / std이며 평균·표준편차와 패딩 채널은 출력 색상 순서를 따른다. 출력은 배치 크기 1의 연속 GPU 텐서다.
- FR-010: GPU uint8 NV12와 HWC RGB/BGR 이미지를 받고 원본을 수정하거나 이미지 데이터를 CPU로 복사하지 않는다. 입력 형식은 pixel_format으로 구분한다. NV12의 기존 색상 변환을 유지하며 정규화를 중복 적용하지 않는다.
- FR-011: 모든 옵션은 선택적 생성자 인자와 YAML 설정을 지원한다. YAML 우선·최초 생성자 기본값 보존·설정 제거 복원을 적용한다. input_name이 없으면 텐서, 있으면 해당 이름의 사전을 model_input에 저장한다.
- FR-012: 기존 별도 스트림·프레임 조기 읽기 완료 신호·보고와 후처리 호환성을 유지한다. 원본 크기, 가로·세로 배율, 패딩 또는 자르기 이동량과 최종 크기를 보관한다. 잘못된 형식·값은 거부한다.

### 경계 사례와 명확화

auto=True는 최소 패딩을 사용하므로 size와 다른 최종 크기를 만들 수 있다. 고정 입력 엔진에서는 auto=False를 사용한다. 여러 입력 모델 전체를 자동 생성하거나 엔진을 읽어 전처리를 자동 추론하지 않는다. RGB/BGR은 HWC의 3채널 uint8 GPU 텐서이며 NV12는 기존 영상 크기 정보를 사용한다.

size는 높이·너비이며 중앙 자르기는 size를 모두 채우는 비율로 리사이즈하고 crop_size로 자른다. crop_size 기본값은 size이고 size보다 클 수 없다. auto, center, stride, scaleup, padding_value는 letterbox에서만 결과에 영향을 준다. 다른 모드의 auto=True와 crop 모드 밖의 crop_size 지정은 구성 오류다. stride는 양의 정수이고 size는 stride 배수로 강제하지 않는다.

평균·표준편차는 채널별 3개이며 표준편차는 양수다. 패딩은 정규화 전 0~255 기준의 스칼라 또는 채널별 3개 값이다. 보간은 bilinear를 사용하고 계산은 FP32, 최종 변환은 지정 자료형으로 수행한다. 기존 NV12 실수 변환을 유지하므로 CPU OpenCV uint8 리사이즈와 비트 단위 일치를 보장하지 않는다.

### 성공 기준

- SC-004: 세 가지 크기 변경·최소 패딩·색상 순서·정규화·두 자료형·두 배치 형식·입력 이름의 수치 및 구성 검증을 통과한다.
- SC-005: 기존 기본 입력·좌표 복원·실제 엔진·비동기 원본 수명·보고 검증에 전처리 변경으로 발생하는 실패가 없다.
- SC-006: 문서에서 탐지용 letterbox와 분류용 중앙 자르기 설정을 보고 각각 입력을 구성할 수 있다.

## 후속 요구사항: 예제 YAML에 전체 옵션 노출

- FR-013: 제공 YAML의 전처리 옵션 노출 요구는 후속 FR-027의 섹션 제거로 대체한다. 기존 예제의 실제 전처리 동작을 유지한다.
- SC-007: 제공 YAML에 전처리 섹션이 없고 예제의 생성자 기본값으로 기존 전처리 설정을 유지한다.

명확화: 전체 옵션 노출은 과거 요청의 이력이다. 현재 제공 YAML에서는 FR-027에 따라 전처리 섹션을 제거하고 소스의 생성자·configure 기능은 유지한다. 다른 YAML 섹션의 사용자 변경은 보존하며 추가 질문은 필요하지 않다.

## 후속 사용자 시나리오 3: 좌표 복원 책임 분리 (2026-10-11, 우선순위 P1)

개발자는 크기 변경 방식을 바꾸어도 후처리의 좌표 계산을 수정하지 않고 원본 영상의 탐지 좌표를 얻는다.

수용 시나리오: 비율 유지 패딩·비균일 늘리기·중앙 자르기 각각에서 모델 입력 기준 박스가 원본 좌표로 복원된다. 후처리는 복원 기능과 원본 크기만 사용하는 다른 변환 객체도 처리한다.

- FR-014: 전처리가 전달하는 변환 객체는 모델 입력 이미지 기준 xyxy 박스를 원본 이미지 기준으로 제자리 복원한다. 축별 배율과 패딩 또는 자르기 이동량을 적용하고 원본 경계로 제한한다. 빈 박스도 처리하고 신뢰도·클래스 열은 보존한다.
- FR-015: 후처리는 변환 객체의 복원 기능을 호출하며 배율·패딩·자르기 방식이나 구체적인 전처리 클래스에 의존하지 않는다. 모델 출력 해석과 NMS는 기존대로 유지한다.
- FR-016: 기존 변환 정보 속성과 CUDA 장치·자료형·스트림·완료 확인·임시 버퍼 정리 계약을 보존한다. 좌표 복원은 CPU 복사나 추가 동기화를 도입하지 않는다.
- SC-008: 세 가지 크기 변경과 비중앙·최소 패딩·확대 제한, 빈 박스·경계 제한·부가 열 보존 수치 검증 및 대체 변환 객체를 사용한 후처리 검증이 통과한다.

명확화 검토: 대화에서 승인한 복원 기능 위임을 적용한다. 좌표는 정규화되지 않은 xyxy이며 크롭으로 사라진 영역은 복구하지 않는다. 기존 균일 배율의 반올림 규칙을 유지한다. 추가 질문은 필요하지 않다.

## 후속 사용자 시나리오: TensorRT 컨텍스트 스트림 통일 (우선순위 P1)

전처리·추론·후처리에서 model_cuda_stream을 없애고 cuda_stream으로 GPU 작업 순서를 연결한다. 추가 질문이 필요한 모호성은 없다. 직접 실행은 전달된 스트림을 사용하고, 공유 배치 작업자의 내부 실행 스트림과 CudaAsync의 일반 관리 기능은 유지한다.

- **FR-031**: TensorRT 전처리는 입력 cuda_stream에서 실행하고 model_cuda_stream을 생성하지 않는다. cuda_stream을 생략하면 현재 GPU 스트림을 선택해 컨텍스트에 제공한다. 기존 스트림 객체는 교체하지 않는다.
- **FR-032**: TensorRTInference는 입력 준비와 개별 추론에 cuda_stream을 사용한다. 배치 실행은 이 스트림에 준비 이벤트를 기록해 내부 작업자에 전달한다. 프레임마다 스트림이 달라져도 결과와 실행 순서를 보존한다.
- **FR-033**: 후처리는 cuda_stream을 사용하고 정리 후에도 이를 유지한다. 모델 입력·출력·좌표 변환·ID 정리와 프레임 해제·타임아웃 안전성은 보존한다.
- **FR-034**: 관련 테스트·문서·공통 HTML 변수 데이터에서 model_cuda_stream 계약을 제거한다. 별도 모델 스트림을 요구한 과거 FR-005는 이번 요청으로 대체한다.
- **SC-014**: 전처리·추론·후처리의 GPU 결과와 기존 스트림 객체가 유지되고 model_cuda_stream이 생성되지 않는다.
- **SC-015**: 개별·배치·전처리·후처리·ID·해제·비동기 관련 회귀가 통과하며 공개 문서에 제거된 입력·출력이 없다.

## 후속 시나리오: 원격 실행 테스트 구성 보완

사용자는 기존에 실패한 두 원격 실행 테스트를 정상 실행하고 싶다. 두 테스트의 가짜 파이프라인에 운영 모드 기본값을 명시한다. 명확화 검토: development=False를 추가한다는 사용자의 승인이 있어 추가 질문은 없다.

- FR-035: 두 원격 실행 테스트는 운영 모드 파이프라인으로 실행되며 사용자 Step 등록 및 중첩 직렬화 검증을 유지한다.
- SC-016: 두 대상 테스트 및 비동기 회귀 테스트 전체가 오류 없이 통과한다.

## 후속 시나리오: CudaAsync 내부 스트림 전달

내부 Step은 하나의 cuda_stream 속성으로 실행 스트림을 받는다. CudaAsync 밖에서는 입력 스트림을 사용한다. 명확화: 사용자가 승인한 내부 교체·외부 복원 방식이며 추가 질문은 없다.

- FR-036: CudaAsync는 입력 준비 완료를 확인하고 작업용 컨텍스트의 cuda_stream을 GPU별 작업자 스트림으로 교체한다. 정상 결과 반영 시 원본 스트림 속성과 속성 부재를 복원한다. 실패·타임아웃에서도 원본 스트림을 유지하며 프레임 수명 안전성을 보존한다.
- FR-037: YOLO는 컨텍스트 cuda_stream을 사용하며 별도 current_model_stream 전달 기능을 제거한다. CudaAsync 없는 TensorRT는 기존 스트림 계약을 유지한다.
- SC-017: 두 내부 Step의 스트림 공유·GPU 작업 완료·원본 복원과 오류·타임아웃·프레임 해제·YOLO·TensorRT 회귀가 통과한다.
