# 기능 명세: YOLO 추론 단계 분리

**작성일**: 2026-10-12
**갱신일**: 2026-10-13
**상태**: 명세 검증 완료
**입력**: 기존 YoloDetect를 유지하면서 TensorRT처럼 분리된 YoloInference를 추가하고, examples/step에 YOLO 전후처리 예제를 구현한다.

## 사용자 시나리오와 검증

### 사용자 이야기 1 - 추론만 연결하기 (우선순위: P1)

파이프라인 작성자는 자신이 준비한 입력을 YOLO 모델에 전달하고 원시 예측을 자신이 선택한 후처리에 전달한다.

**우선순위 이유**: 전처리와 후처리를 개별 단계로 교체할 수 있어야 한다.
**독립 검증**: 준비된 입력을 전달했을 때 원시 예측과 실행 식별자를 받고 원본과 기존 감지 결과가 유지되는지 확인한다.

**인수 시나리오**:
1. 전처리된 입력이 있을 때 추론하면 원시 예측을 얻으며 감지 결과를 생성하거나 덮어쓰지 않는다.
2. 추론 간격에 해당하지 않는 입력은 식별자를 전달하고 이전 예측을 제거한다.
3. 잘못된 입력이나 모델 실행 실패는 명확한 오류로 호출자에게 전달한다.

### 사용자 이야기 2 - 공유 배치와 기존 파이프라인 유지 (우선순위: P2)

작성자는 공유 배치 또는 비동기 실행을 선택하고 기존 YoloDetect 파이프라인도 계속 사용한다.

**우선순위 이유**: 기존 운영 동작과 공유 모델 실행 방식을 유지한다.
**독립 검증**: 두 요청의 입력을 결합한 뒤 각각 독립적인 예측을 받으며 기존 감지 테스트가 통과한다.

**인수 시나리오**:
1. 공유 배치는 모델·GPU·입력 자료형·형상이 호환되는 요청만 결합하고 각 요청에 자기 결과를 반환한다.
2. 기존 YoloDetect 생성자와 실행 결과는 바뀌지 않는다.
3. 비동기 실행 및 YOLO 보고에서 새로운 추론 단계도 인식한다.

### 사용자 이야기 3 - YOLO 전후처리와 전체 보고 연결 (우선순위: P1)

작성자는 YoloPreProcess → YoloInference → YoloPostProcess를 연결하여 GPU 감지 결과를 얻고 YoloReport에서 전체 처리 구간을 확인한다.

**우선순위 이유**: 새 추론 단계와 바로 연결할 수 있는 전후처리와 일관된 보고가 필요하다.
**독립 검증**: GPU 이미지부터 감지 결과까지 연결하고 세 단계가 완료 표본 하나에 기록되는지 확인한다.

**인수 시나리오**:
1. GPU NV12/RGB/BGR 이미지가 주어지면 YOLO 입력과 좌표 변환 정보를 만들고 원본 읽기 종료를 알린다.
2. 원시 예측이 주어지면 신뢰도·클래스 필터와 NMS를 적용하고 좌표를 복원하여 모델별 감지 결과를 저장한다.
3. 추론 건너뜀은 해당 모델 결과만 None으로 갱신하고 임시 정보를 제거한다.
4. 개별·공유 배치 및 비동기 실행에서 전처리·추론·후처리를 YOLO 보고 한 표본에 기록한다.
5. 기본 COCO 또는 지정한 사용자 클래스 이름으로 감지 결과를 해석하고 잘못된 설정·출력은 명확한 오류로 전달한다.
6. YOLO 전처리는 Step을 직접 상속하고 TensorRT 전처리 예제를 가져오지 않아도 독립적으로 사용할 수 있다.

### 사용자 이야기 4 - 추론 백엔드만 교체 (우선순위: P1)

작성자는 같은 감지 모델의 전처리와 후처리를 유지하고 YoloInference의 backend만 교체한다.

**우선순위 이유**: 백엔드별 임시 필드와 처리 차이로 전후처리를 다시 작성할 필요가 없어야 한다.
**독립 검증**: 같은 전후처리와 모델 규칙으로 두 추론 백엔드를 개별·공유 배치로 연결하여 컨텍스트 계약·감지 결과·보고 백엔드를 확인한다.

**인수 시나리오**:
1. 두 경로는 model_input, model_output, model_id, image_transform 및 detections를 공통으로 사용한다.
2. 이름 있는 단일 입력 사전은 YOLO와 TensorRT 모두 실행하며 실행부가 지원하는 YOLO 다중 입력도 전달하며 지원하지 않는 실행부는 명확한 오류로 거부한다.
3. 어떤 계열의 전후처리 예제를 사용하든 동일 옵션으로 같은 결과를 해석하며 FP16·사용자 이름·end2end를 지원한다.
4. 전후처리 보고는 실제 추론 백엔드의 완료 표본 하나에 기록하고 비동기 건너뜀·오류·부분 종료도 같은 기준을 적용한다.
5. 기존 사용자 단계가 전달한 이전 좌표·프로파일 필드도 읽을 수 있으며 후처리는 공통/이전 임시 필드를 모두 정리한다.

### 추가 경계 사례

- 입력 누락, CPU 입력, GPU/스트림 불일치, 빈 입력 형상·잘못된 공유 배치 크기는 오류다. 입력의 채널·차원·자료형은 모델 실행부가 검증한다.
- 건너뛴 입력은 모델을 로드하지 않고 이전 원시 결과를 제거한다.
- 배치 실패는 모든 관련 호출에 오류를 전달하고 다음 요청에서 모델을 다시 준비한다.
- 출력 GPU 불일치는 오류다. 공유 배치 출력은 배치 축도 검증하며 실패한 GPU 작업은 정리한다.
- 감지 없음은 빈 boxes 결과이고, 미실행은 해당 ID의 None 결과다. 다른 모델의 결과는 유지한다.
- 후처리 실패 시 임시 입력·출력·좌표 변환·식별자·보고 정보를 정리한다.

## 요구사항

### 기능 요구사항

- **FR-001**: YoloInference를 공개 파이프라인 단계로 추가하고 전처리된 입력에서 원시 YOLO 감지 예측을 생성한다.
- **FR-002**: 색 변환·리사이즈·정규화·NMS·좌표 복원·감지 결과 저장은 호출자의 전후처리가 담당한다.
- **FR-003**: GPU, 추론 간격, 식별자 설정 및 생성자 기본값과 YAML 덮어쓰기를 지원한다.
- **FR-004**: 입력 및 출력 계약을 검증하고 GPU 실행 완료와 실패 정리를 보장한다.
- **FR-005**: 공유 배치에서 호환 요청을 결합하고 독립적인 요청별 결과를 반환한다.
- **FR-006**: YoloDetect는 변경 없이 유지하고 비동기 실행 및 기존 성능 보고에 연결한다.
- **FR-007**: 사용법과 계약을 한글 문서로 제공하고 신규 계약 및 기존 호환성을 테스트한다.
- **FR-008**: examples/step의 YoloPreProcess는 GPU 이미지로부터 FP32/FP16 RGB 배치 1 입력과 좌표 변환 정보를 만들고 프레임 사용 종료를 알린다.
- **FR-009**: examples/step의 YoloPostProcess는 설정 가능한 신뢰도·클래스·IoU·최대 감지 수·이름으로 필터/NMS/좌표 복원을 수행하고 detections[model_id]를 기록한다.
- **FR-010**: 전후처리는 생성자 기본값과 클래스별 YAML 설정을 적용하며 잘못된 설정·입출력을 검증하고 임시 상태를 정리한다.
- **FR-011**: 새 전후처리와 추론은 YoloReport의 전체 YOLO 표본을 공유하고 완료·건너뜀·오류·비동기 부분 종료를 중복 없이 기록한다.
- **FR-012**: 사용 중인 단일 스트림 예제의 새 단계 가져오기와 YOLO 보고 연결을 완성한다.
- **FR-013**: YoloPreProcess는 Step을 직접 상속하고 TensorRTPreProcess를 상속하거나 가져오지 않는다. 백엔드 중립 공통 도우미를 사용해 GPU 변환·프레임 해제 계약을 유지한다.
- **FR-014**: 추론 입출력과 실행 식별자는 model_input/model_output/model_id로, 전처리 좌표 정보는 image_transform으로 통일한다. YOLO도 이름별 GPU 입력 사전을 받으며 실행부의 다중 입력 지원 규칙을 따른다.
- **FR-015**: 두 전후처리 예제는 공통 GPU 구현과 같은 옵션·기본값을 제공한다. 후처리 기본 클래스는 모두 None이며 FP32/FP16·사용자 names·end2end를 지원한다. 실제 모델 자료형·형상·이름 요구는 각 백엔드가 검증한다.
- **FR-016**: 공통 프로파일을 추론 백엔드에 연결하여 전후처리를 실제 백엔드의 한 표본에 기록하고 CudaAsync 상태도 실제 추론 단계로 분류한다.
- **FR-017**: 이전 좌표/프로파일 필드는 입력 호환성을 위해 읽을 수 있지만 새 전처리는 공통 필드만 생성한다. 오류와 건너뜀을 포함한 후처리 종료에서 공통·이전 임시 정보를 모두 정리한다.

### 주요 개체

- 모델 입력: 전처리 단계에서 준비된 GPU 텐서 또는 이름별 GPU 텐서 사전.
- 원시 예측: 후처리가 해석하는 GPU 예측과 모델 실행 식별자.
- 공유 요청: 입력, GPU 완료 신호, 결과, 실패 상태를 갖는다.
- 이미지 변환: 원본 크기와 크기 변경 비율·패딩을 보관하여 감지 좌표를 복원한다.
- 감지 결과: 모델 ID별 boxes·클래스 이름·원본 크기와 전체 처리 보고를 갖는다.

## 성공 기준

- **SC-001**: 준비된 입력, 간격 건너뜀, 입력 오류, 공유 배치의 네 시나리오 검증이 모두 통과한다.
- **SC-002**: 기존 감지 파이프라인의 관련 회귀 검증에서 신규 실패가 없다.
- **SC-003**: 문서의 전처리 → 추론 → 후처리 연결 예제로 실행 계약을 확인할 수 있다.
- **SC-004**: 새 전후처리의 GPU 변환·NMS·좌표 복원·설정·오류·건너뜀 검증이 모두 통과하고 실제 모델 연결에서 세 구간이 완료 표본 하나로 기록된다.
- **SC-005**: TensorRT 전처리 예제 모듈을 차단한 상태에서도 YOLO 전처리를 가져와 생성할 수 있고 기존 YOLO 처리 검증이 통과한다.
- **SC-006**: 전후처리 조합을 두 백엔드와 교차 연결한 검증, 이름 있는 입력, 실제 GPU 모델, 보고 및 임시 정리 검증이 모두 통과한다.

## 가정

- TensorRT와 같은 분리는 model_input → model_output 및 model_id 계약을 뜻한다.
- 모든 원시 GPU 출력과 중첩 보조 출력을 보존한다. 감지·분할·포즈 결과의 해석은 모델별 후처리가 담당한다.
- 기본 실행은 개별 추론이며 공유 배치는 요청당 이미지 한 장이다.
- 두 전후처리 예제 이름과 Step 직접 상속은 유지하고 구현·계약·기본값을 공통화한다. 기본은 COCO 감지 모델이며 사용자 이름을 지정할 수 있다. 분할·포즈 전용 결과 해석은 범위 밖이다.
- 보안·저장소·서비스 배포는 변경하지 않는다. 확장 훅은 등록되어 있지 않다.

## 명확화 검토

2026-10-12: 기능 범위, 데이터, 오류, 통합, 용어, 완료 조건을 검토했다. 기존 TensorRT 계약으로 합리적인 기본값을 결정할 수 있어 질문이 필요한 주요 모호성은 없다.

2026-10-12 추가 요청: 새 YOLO 전후처리와 전체 보고를 범위에 포함했다. 기본 신뢰도 0.25·IoU 0.7·최대 감지 300·모든 클래스·640 정방형 letterbox를 사용한다. 기존 GPU 전처리와 YOLO 보고 계약으로 질문이 필요한 주요 모호성은 없다.

2026-10-12 상속 변경 요청: YoloPreProcess가 Step을 직접 상속하고 필요한 GPU 변환 및 설정 검증을 자체 구현하도록 한다. 변경 범위와 유지할 동작이 명확하여 추가 질문은 필요하지 않다.

2026-10-12 공통 계약 요청: image_transform과 내부 공통 프로파일로 연결을 통일하고 두 예제는 공통 구현을 사용한다. TensorRT 후처리의 기존 기본 차량 필터 [2]는 모든 클래스 None으로 통일하며 차량만 필요하면 명시적으로 classes=[2]를 설정한다. 형상·자료형·실제 입력/출력 이름은 모델별 차이를 유지한다. 이전 임시 필드는 입력 호환용으로만 읽는다. 합의된 방향과 기존 구조로 결정 가능하여 추가 질문은 필요하지 않다.

## 사용자 이야기 5 - 라이브러리에서 독립적인 GPU 전용 추론 (우선순위: P1)

작성자는 YOLO 구현 라이브러리와 독립적인 실행부를 선택하여 준비된 GPU 입력을 실행하고 모든 원시 출력을 후처리로 전달한다.

**독립 검증**: 특정 YOLO 라이브러리를 가져올 수 없는 환경에서 두 개의 이름 있는 GPU 입력과 여러 출력을 실행한다. CPU 입력·출력·모델 내부 CPU 전환을 거부한다.

**인수 시나리오**:
1. 기본 실행은 특정 YOLO 라이브러리를 요구하지 않으며 다른 실행부를 생성자와 단계 YAML에서 선택한다.
2. 입력의 채널·형상·자료형·개수는 특정 감지 모델 값으로 고정하지 않고 실행부의 모델 규약을 따른다.
3. 사전 출력 이름을 유지하고 중첩 출력의 모든 텐서를 결정적인 경로 이름으로 전달하며 비텐서·빈 출력·이름 충돌은 오류다.
4. GPU가 없거나 CPU 텐서·다른 GPU 텐서를 사용하면 명확한 오류를 반환하며 CPU 실행으로 전환하지 않는다.
5. 기존 모델은 명시적인 호환 실행부로 계속 실행하고 주 감지 출력은 기존 후처리와 연결된다.
