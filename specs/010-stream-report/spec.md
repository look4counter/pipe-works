# 기능 명세: 실행별 프레임 처리 보고

## 기록 비용 절감 (2026-10-10)

- FR-026: 기록 함수는 누적값과 최근 표본만 갱신하고 매 호출에 전체 스냅샷이나 단계별 사전·튜플을 재생성하지 않는다.
- FR-027: 활성 보고자들의 스냅샷은 프로세스 공용 발행 작업자 하나가 100ms 주기로 생성한다. 마지막 보고자 종료 시 작업자와 등록을 정리한다. 최신 표시의 약 100ms 지연은 허용하며 정확한 10초 표본 경계 계산과 누적 기록 무손실을 유지한다. OS 스케줄링 지연은 추가될 수 있다.
- FR-028: StreamReport가 없는 파이프라인은 공통 StreamReport 기록의 잠금·시계·이력 수집을 건너뛴다. 별도 감지 프로파일링은 유지한다. 직접 기록 함수 검증용 report_scope는 기본 활성 수집을 유지한다.
- SC-013: 스냅샷 생성 빈도와 무리포트 무수집, 다중 기록·보고자·발행 종료를 검증하고 같은 조건의 기록 함수 4회 비용을 이전 구현과 비교한다. 전체 파이프라인 성능 개선률은 주장하지 않는다.

명확화: 독립 발행 작업자는 통계 잠금을 사용하지만 읽기·출력 작업자는 사용하지 않는다. 매 기록 불변 객체 생성과 새 집계 스레드 미추가라는 이전 설계는 대체한다. 내부 구조가 알려진 Hotswap·Tap·CudaAsync 중첩 보고자도 감지한다. 추가 질문은 없다.

**기준**: 현재 `src/pipeworks/embedded/stream_report.py`와 인접 단계의 동작

## 사용자 시나리오

사용자는 `StreamReport`를 마지막 단계에 배치해 약 1초마다 영상별 FPS, 프레임 처리 시간, 추론 시간과 실행된 단계의 지연을 확인한다. 다른 파이프라인의 수치는 섞이지 않는다.

### 시나리오: 마지막 단계의 영상 상태 보고

사용자는 `RTSPPublish` 뒤에 `StreamReport`를 마지막 Step으로 추가한다. 송출 단계가 출력 컨텍스트를 만들지 않아도 보고는 약 1초마다 계속 표시된다. 처리 지표와 실제 패킷 수신·송신 성공 상태를 확인한다.

**인수 조건**:

1. 첫 성공 전에는 수신·송신을 대기로 표시하고, 성공 패킷이 있으면 성공으로 표시한다.
2. 수신 또는 송신 오류가 발생하면 실패로 표시하고, 성공 패킷이 5초 이상 없으면 중단으로 표시한다.
3. FPS, 평균 프레임 처리 시간, 평균 추론 시간과 건수 및 기록된 단계별 평균을 표시한다. 입력 프레임이 없는 구간도 상태를 표시한다.
4. 마지막 Step은 상류 실행을 계속 소비하고, 종료 시 보고 작업을 정리한다. 다른 파이프라인의 출력이나 통계와 섞이지 않는다.

## 기능 요구사항

- **FR-001**: `NvidiaDecode`는 출력 프레임의 처리 시작 시각을 컨텍스트에 기록해야 한다.
- **FR-002**: `NvidiaEncode`는 시작 시각이 있는 프레임의 처리 시간과 인코딩 호출 시간을 기록해야 한다. 시작 시각이 없어도 인코딩은 계속해야 한다.
- **FR-003**: 통계는 `Pipeline._run_local` 실행별 수집기에 기록하고, 여러 기록 스레드의 갱신은 잠금으로 보호해야 한다. 보고 측은 발행된 불변 통계만 읽으며 수집기 잠금을 획득하지 않는다. 실행 문맥이 없는 독립 Step 호출은 기본 수집기를 사용한다.
- **FR-004**: `StreamReport`는 약 1초마다 완료 프레임 수를 실제 경과 시간으로 나눈 FPS와 평균 처리 시간을 출력해야 한다.
- **FR-005**: `StreamReport`는 받은 패킷 컨텍스트를 같은 객체로 다음 단계에 전달해야 한다.
- **FR-006**: `YoloDetect`와 `YoloDetectBatch`는 시작된 추론 요청의 경과 시간을 공통 추론 건수와 평균에 기록해야 한다.
- **FR-007**: 배치 입력 대기, 배치 내부 대기, 인코딩, 송출 시간은 해당 단계가 실제 실행된 경우에만 단계별 평균에 포함해야 한다.
- **FR-008**: 보고는 표준 출력에 FPS·프레임 처리 시간·추론 요약 첫 줄과 사용 가능한 단계별 평균 둘째 줄을 기록해야 한다. `details` 설정이나 터미널 종류에 따른 출력 분기는 사용하지 않는다.
- **FR-009**: 공개 보고 단계는 `StreamReport`만 제공한다. 기존 통계 기록 함수와 그 구현 모듈 `stream_report.py`는 유지한다.
- **FR-010**: `StreamReport`를 공개 Step으로 제공하고, 출력이 없는 `RTSPPublish` 뒤에 마지막으로 배치해도 정기적으로 보고해야 한다. 기존 두 줄 보고 형식과 처리 지표를 포함해야 한다.
- **FR-011**: RTSP 소스는 실제 비디오 패킷 수신 성공과 수신 실패를, 송출 단계는 실제 패킷 송신 성공과 송신 실패를 실행별 수집기에 기록해야 한다.
- **FR-012**: `StreamReport`는 수신·송신 상태를 각각 대기·성공·실패·중단으로 표시해야 한다. 최근 성공이 5초를 넘으면 중단이며 명시적 실패는 즉시 실패로 표시한다.
- **FR-013**: `StreamReport`의 정기 출력은 입력 프레임이 없을 때도 동작하고, 호출자의 표준 출력으로 전달되며, 종료할 때 보고 작업자를 정리해야 한다.
- **FR-017**: 폐기한 보고 단계의 공개 내보내기를 제거하고, 보고 동작 검증은 `StreamReport`를 기준으로 유지해야 한다.
- **FR-018**: 보고 기능의 모듈 경로와 명세 이름에서도 폐기한 단계 이름을 제거하고 `StreamReport` 기준으로 통일해야 한다. 기존 통계 기록과 보고 동작은 유지한다.

## 성공 기준

- **SC-001**: 완료된 프레임 수와 처리 시간의 평균이 보고 구간의 FPS와 밀리초 값에 반영된다.
- **SC-002**: 두 YOLO 단계가 같은 형식의 추론 건수와 평균 시간을 기록한다.
- **SC-003**: 실행되지 않은 단계의 평균은 표시되지 않고, 서로 다른 파이프라인의 통계가 섞이지 않는다.
- **SC-004**: 입력 패킷 컨텍스트의 객체 동일성과 개수가 유지되며, 시작 시각이 없는 입력도 인코딩된다.
- **SC-005**: 표준 출력 대상에 관계없이 두 줄 상세 보고를 출력한다.
- **SC-006**: `RTSPPublish` 뒤에 둔 `StreamReport`가 상류 출력이 없어도 1초 간격으로 수신·송신 상태와 FPS·평균 처리·추론 지표를 출력한다.
- **SC-007**: 정상 패킷, 오류, 5초 이상 무응답의 상태 전환이 수신과 송신에 독립적으로 반영된다.
- **SC-008**: 동시 파이프라인 보고가 분리되고 종료 후 보고 작업자가 남지 않는다.

## 범위

### 추론 시간 명확화 (2026-10-04)

**명확화 결정**: 사용자가 말한 추론 요청은 공유 작업자의 대기열 등록이 아니라 실제 모델 예측 호출을 뜻한다. 여러 프레임을 함께 실행할 때 각 요청에는 같은 배치 실행 시간을 표시한다.

- **FR-014**: 평균 추론 시간은 실제 모델 예측 호출이 시작된 순간부터 그 호출의 GPU 작업이 완료된 순간까지의 시간으로 계산해야 한다. 요청 대기, 배치 구성, 입력 준비, 첫 모델 로드, 결과 변환은 제외한다.
- **FR-015**: 배치 추론에서는 배치 전체의 실제 모델 실행 시간을 각 참여 요청의 추론 시간으로 기록한다. 배치 시간을 요청 수로 나누거나 합산하지 않는다.
- **FR-016**: 모델 예측이 시작되기 전에 실패한 요청은 추론 건수와 평균에 포함하지 않는다. 기존 추론 결과 반환 계약은 유지한다.

**검증 기준**: 의도적으로 늘린 배치 대기와 입력 준비 시간이 평균 추론 시간에 반영되지 않고, 모델 예측 실행 시간만 각 요청에 기록된다.

프레임 처리 시간은 디코더가 프레임을 내보낸 뒤 인코더 호출이 끝날 때까지다. RTSP 송출 시간은 별도 단계 평균이다. FPS는 완료된 인코딩 프레임 기준이다.

보고 단계는 `StreamReport` 하나만 사용한다. 수신 성공은 유효 비디오 패킷을 받은 때, 송신 성공은 패킷 송신이 완료된 때로 정의한다.
## 1초·최근 10초 동시 표시

- FR-020: 프레임처리(1초)·프레임처리(최근10초)·추론(1초)·추론(최근10초)를 함께 표시한다. 기존 출력 주기·FPS·단계별 시간은 유지한다.
- FR-021: 최근 10초는 완료 시각이 최근 10초 구간에 포함된 표본의 시간 합을 전체 완료 건수로 나눈 가중 평균이다. 프레임과 추론은 별도로 집계한다. 만료 표본은 정리하고 실행별 격리를 유지한다.
- SC-010: 불균등 건수·10초 경계·1초 구간 차분·빈 구간과 추론 없는 구간·실행별 격리 검증이 통과한다.

명확화: 처음 10초가 차지 않았으면 현재까지의 표본을 사용하며 표본이 없으면 없음으로 표시한다. 최근 구간은 (현재-10초, 현재]이며 기존 1초 집계는 출력 간 실제 구간이다. 추가 질문은 필요하지 않다.
## 출력 표기 변경

- FR-022: 평균 계산을 유지하고 프레임처리 값/1s, 값/10s 및 추론 값/1s, 값/10s 형태로 묶어 출력한다. 표본 없는 추론과 최근 프레임은 없음/구간으로 표시한다. 추론 건수는 기존처럼 유지한다.

명확화: 사용자가 승인한 표기는 프레임처리 15.3ms/1s, 14.3ms/10s이다. 단위 뒤 기간은 집계 구간을 의미한다. 추가 질문은 필요하지 않다.

## 읽기 전용 보고 (2026-10-10)

### 사용자 이야기: 처리 경로를 잠그지 않는 보고 (우선순위 P1)

사용자는 기존 `StreamReport` 출력과 실행별 통계를 유지하면서 보고서 조회가 기록 스레드를 잠금으로 기다리게 하지 않기를 원한다. 보고서는 수집기의 집계를 초기화하거나 공유 이력을 변경하지 않는다.

인수 조건: 기록 후 두 독립 보고자가 각각 같은 구간 통계를 읽을 수 있고, 한 보고자의 조회가 다른 보고자의 값을 소모하지 않는다. 입력 중단 중에도 만료 기록과 수신·송신 상태가 현재 보고 시각에 맞게 표시된다.

- FR-023: 독립 발행 작업자는 일관된 불변 스냅샷을 발행하고, StreamReport 보고자의 시작·주기 조회는 통계 잠금을 획득하거나 공유 집계·이력을 변경하지 않아야 한다.
- FR-024: 프레임·추론·단계별 누적 건수와 시간 합은 보고 때문에 초기화하지 않는다. 각 보고자는 이전 관측값과의 차이로 직전 출력 간 실제 구간의 지표를 계산한다.
- FR-025: 기존 정확한 최근 10초 가중 평균과 빈 구간 표시를 유지한다. 기록이 없는 동안에도 만료 표본을 평균에서 제외하고, 기록 측의 이력 보관량은 현재 보관 구간의 표본 수에 비례하도록 제한한다.
- SC-011: 통계 잠금 획득 시 실패하도록 설정한 수집기에서도 StreamReport의 시작·조회·주기 출력이 성공하고, 조회 전후 발행된 스냅샷과 누적값이 바뀌지 않는다.
- SC-012: 다중 기록 스레드의 최종 누적값, 독립 보고자, 무입력·10초 경계와 불균등 표본 수를 결정적 테스트로 검증하고 기존 보고·감지·중앙 출력 회귀가 통과한다.

명확화: 대화에서 읽기 전용 역할과 보고 측 잠금 제거가 확정되어 추가 질문은 없다. 기록 측의 잠금, 출력·IPC 내부 동기화, 별도 감지 보고 단계의 잠금은 변경 범위 밖이다. 보고 계산은 각 보고자의 관측 상태만 갱신할 수 있다. 전체 처리 성능 향상 수치는 보장하지 않으며 변경 목표는 보고자와 기록자 사이의 통계 잠금 경합 제거다.
