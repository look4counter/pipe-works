# 기능 명세: 중앙 스트림 프로세스

**작성일**: 2026-10-03
**상태**: 확정

## 사용자 시나리오

### 1. 기존 호출로 중앙 실행

사용자는 기존 방식으로 파이프라인을 구성하고 `run()`을 호출한다. 영상 처리와 GPU 작업은 하나의 중앙 프로세스에서 수행된다. 호출은 스트림이 끝날 때까지 대기한다.

- 정상 종료 시 호출도 정상 반환한다.
- 실행 오류 시 호출자에게 실패를 알린다.

### 2. 호출자 종료에 따른 스트림 종료

사용자가 호출을 중단하거나 호출자 프로세스를 종료하면 중앙 프로세스의 해당 스트림이 종료된다. 다른 호출자의 스트림은 계속 실행된다.

### 3. 여러 스트림 동시 실행

서로 다른 호출자가 동시에 요청한 스트림을 중앙 프로세스가 함께 실행한다. 영상 프레임은 프로세스 사이로 전달되지 않는다.

## 예외 상황

- 중앙 프로세스에 연결할 수 없으면 실행 실패를 알린다.
- 중앙 프로세스가 실행 중 종료되면 모든 대기 중 호출자에게 실패를 알린다.
- 스트림 하나가 실패해도 다른 스트림은 유지한다.
- 직렬화할 수 없는 사용자 정의 단계는 명확한 오류로 거부한다.

## 요구사항

- **FR-001**: 기존 `Pipeline(...).step(...).run()` 호출 방식을 유지한다.
- **FR-002**: 모든 파이프라인의 영상 및 GPU 처리를 중앙 프로세스 안에서 실행한다.
- **FR-003**: `run()`은 해당 스트림 종료까지 대기하고 정상 완료와 실패를 구별한다.
- **FR-004**: 호출 중단 또는 호출자 종료 시 해당 스트림을 정리하며 다른 스트림은 유지한다.
- **FR-005**: 사용자 정의 단계를 포함한 파이프라인을 중앙 프로세스에 전달할 수 있다.
- **FR-006**: 같은 모델을 사용하는 배치 추론은 중앙 프로세스 안에서 공유한다.
- **FR-007**: 서로 다른 Windows 사용자 계정의 중앙 프로세스 주소가 충돌하지 않아야 한다.
- **FR-008**: 중앙 프로세스 시작에 실패하면 호출자에게 실제 시작 오류를 알린다.

## 성공 기준

- 두 호출자의 파이프라인이 동일한 중앙 프로세스에서 실행됨을 확인할 수 있다.
- 한 호출자를 종료한 뒤 해당 스트림이 정리되고 다른 스트림은 계속 실행된다.
- GPU 텐서가 프로세스 간 전송되지 않는다.
- 기존 예제의 `run()` 호출 코드를 바꾸지 않고 실행할 수 있다.

## 가정

- 로컬 Windows 호스트의 신뢰할 수 있는 사용자만 중앙 프로세스에 요청한다.
- 사용자 정의 단계의 강제 중단은 일반화할 수 없으므로 종료 요청은 협조적이며, 블로킹 작업은 자체 시간 제한에 따른다.
# 호출자 콘솔 출력 추가 요구사항

## 사용자 시나리오

사용자가 `examples/01_single_stream_rtsp_style.py`를 콘솔에서 실행하면 `PostProcess` 등 사용자 정의 Step의 `print()` 결과가 그 콘솔에 실행 중 순서대로 표시된다. 별도의 콘솔에서 실행한 파이프라인의 출력은 섞이지 않는다.

## 명확화 결과와 가정

- 출력 범위는 해당 파이프라인의 실행 스레드와 `Sink`가 생성한 작업 스레드의 표준 출력이다. 사용자가 직접 생성한 임의 스레드는 이번 범위에 포함하지 않는다.
- 호출자의 표준 출력이 리디렉션되어 있으면 해당 출력 대상에 기록한다.
- 중앙 프로세스의 기존 오류 전달과 호출 종료 시 정리 동작을 유지한다.

## 추가 기능 요구사항

- **FR-009**: Step이 실행 중 표준 출력에 기록한 내용은 해당 `run()` 호출자의 표준 출력에 표시되어야 한다.
- **FR-010**: 동시에 실행하는 파이프라인의 출력은 각자의 호출자에게만 전달되어야 한다.
- **FR-011**: 출력 전달 후에도 정상 완료, 실행 오류 및 호출자 종료 동작이 유지되어야 한다.

## 추가 성공 기준

- **SC-001**: 두 호출자가 각각 고유한 문구를 출력하는 경우 각 호출자에게 자기 문구만 표시된다.
- **SC-002**: `run()`이 끝나기 전에 Step 출력이 호출자에게 표시된다.

## Sink 작업 스레드 출력 보완

- **FR-016**: `Sink` 안의 사용자 정의 Step이 출력한 내용도 해당 `run()` 호출자의 표준 출력에 표시되어야 한다.
- **FR-017**: 동시에 실행하는 서로 다른 `Sink`의 출력이 각 호출자에게만 전달되어야 한다.
- **SC-005**: `Sink(PostProcess())`가 출력한 문구와 `StreamReport` 출력이 같은 호출자 콘솔에 나타난다.

## GPU 큐 동기화 보완

- **FR-018**: `YoloDetectBatch`는 선택한 프레임의 GPU 복제 완료를 기다리느라 파이프라인 CPU 스레드를 동기화하지 않아야 한다.
- **FR-019**: 내부 배치 작업자는 GPU 복제가 끝난 후에만 복제본을 읽어야 한다.
- **FR-020**: 입력과 출력 프레임의 순서, 설정된 추론 간격, 모델별 배치 묶음은 유지되어야 한다.
- **SC-006**: 선택 프레임 처리 경로에서 CUDA 스트림의 호스트 동기화 호출이 없고, 실제 GPU 추론 결과가 올바르다.

## 프레임 지연 원인 표시

- **FR-021**: 프레임 보고는 배치 입력 대기, 배치 내부 대기, 인코딩, 송출 시간을 구분하여 표시해야 한다.
- **FR-022**: 기존 FPS, 프레임 처리 시간 및 추론 건수 표시는 유지되어야 한다.
- **FR-023**: 단계별 시간은 해당 단계가 실제로 실행된 경우만 평균에 포함해야 한다.
- **SC-007**: 한 영상의 프레임 처리 시간이 증가할 때 사용자는 보고 줄에서 배치 이전 대기, 배치 내부 대기, 인코딩 및 송출 중 시간이 큰 구간을 확인할 수 있다.

## 단일 영상 지연 최소화

- **FR-024**: 배치 Step은 입력을 미리 읽거나 프레임을 보관하지 않고 선택 프레임의 추론 결과를 기다려야 한다.
- **FR-025**: 배치 Step은 같은 프로세스의 모델별 요청 큐와 GPU 텐서를 사용하고 추론 간격, 오류 시 프레임 통과, 원본 순서를 유지해야 한다.
- **FR-026**: 배치 Step은 건너뛴 프레임과 선택 프레임을 원래 순서대로 모두 전달해야 한다.
- **SC-008**: 30fps 단일 입력과 15ms 추론에서 배치 내부 대기는 선택 프레임의 추론 시간에 가깝고, 건너뛴 프레임에는 다음 입력 대기가 추가되지 않는다.
# GPU 내부 배치 추론 요구사항

## 사용자 시나리오

여러 스트림이 같은 YOLO 모델을 사용해도 중앙 프로세스 안의 모델과 배치 큐를 공유한다. 각 스트림의 GPU 프레임은 CPU 영상 복사나 별도 YOLO 프로세스 없이 추론되고, 감지 결과도 GPU에 남는다.

## 명확화 결과와 가정

- 중앙 프로세스 안에서는 프로세스 간 GPU IPC 대신 같은 프로세스의 GPU 텐서를 직접 공유한다.
- 범위는 `YoloDetectBatch`의 입력 변환, 배치 추론과 결과 전달이다. 별도 `YoloDetect` 단계는 포함하지 않는다.
- 기존 배치 크기, 대기 시간, 옵션별 분리, 추론 간격과 오류 시 프레임 통과 동작을 유지한다.

## 추가 기능 요구사항

- **FR-012**: `YoloDetectBatch`는 별도 YOLO 작업자 프로세스를 시작하거나 사용하지 않아야 한다.
- **FR-013**: NV12 입력을 GPU에서 모델 입력으로 변환하고 영상 데이터를 CPU로 복사하지 않아야 한다.
- **FR-014**: 배치 결과의 감지 좌표는 원본 영상 크기에 맞고 GPU에 남아야 한다.
- **FR-015**: 같은 모델 요청은 중앙 프로세스 안의 모델과 배치 큐를 공유하고 기존 배치 설정을 지켜야 한다.

## 추가 성공 기준

- **SC-003**: `.pt`와 `.engine` 실제 추론에서 입력과 감지 좌표의 장치가 GPU이며 별도 YOLO 프로세스가 생성되지 않는다.
- **SC-004**: 서로 다른 스트림의 호환 요청이 한 배치로 처리되고 요청별 결과 크기가 정확하다.
## 실행별 통계 분리

### 사용자 시나리오

사용자가 01과 02 예제를 각각 실행하면 각 실행의 프레임 수, 추론 수, 처리 시간과 단계별 지연은 해당 실행의 보고에만 반영된다. 동일한 파이프라인 이름으로 동시에 실행해도 통계가 섞이지 않는다.

### 요구사항

- **FR-027**: 중앙 프로세스에서 동시에 실행되는 파이프라인의 통계를 실행별로 분리해야 한다.
- **FR-028**: 배치 추론 시간은 결과를 기다리는 파이프라인 실행 스레드에서 측정하여 해당 실행의 통계에 귀속해야 한다.
- **FR-029**: 보고 기능이 없는 실행의 통계는 다른 실행의 보고에 반영되지 않아야 한다.

### 성공 기준

- **SC-009**: 두 실행이 겹치는 동안 한 실행의 프레임 및 추론 기록을 추가해도 다른 실행의 보고 수치와 단계별 평균이 변하지 않는다.
## 연결이 없는 중앙 프로세스 종료

### 사용자 시나리오

사용자가 실행한 모든 파이프라인이 끝나거나 호출 프로세스와의 연결이 끊기면 중앙 프로세스도 자동으로 종료된다. 다른 파이프라인이 아직 연결되어 있으면 계속 처리한다.

### 요구사항

- **FR-030**: 활성 파이프라인 연결이 하나도 없는 상태가 되면 중앙 프로세스를 자동 종료해야 한다.
- **FR-031**: 시작 확인용 연결은 활성 파이프라인 연결로 취급하지 않아야 한다.
- **FR-032**: 마지막 연결 해제 직후 새 파이프라인이 연결되면 중앙 프로세스는 실행을 유지해야 한다.

### 성공 기준

- **SC-010**: 두 호출자가 연결된 상태에서 하나가 종료되어도 중앙 프로세스는 유지되고, 마지막 호출자가 종료되면 짧은 유예 시간 뒤 종료된다.
## 중앙 프로세스 콘솔창 숨김

### 사용자 시나리오

사용자가 예제 파이프라인을 콘솔에서 실행하면 중앙 프로세스가 추가 콘솔창을 표시하지 않는다. 예제의 출력과 중앙 프로세스 시작 오류는 기존처럼 호출자에게 전달된다.

### 요구사항

- **FR-033**: Windows에서 자동으로 시작한 중앙 프로세스는 별도 콘솔창을 만들지 않아야 한다.
- **FR-034**: 콘솔창 숨김 적용 후에도 Step 출력과 시작 실패 진단 정보가 호출자에게 전달되어야 한다.
- **FR-035**: 창 없는 Python 실행 파일이 없는 환경에서도 중앙 프로세스가 창 없이 시작되어야 한다.

### 성공 기준

- **SC-011**: 실제 중앙 프로세스에서 콘솔 핸들이 없으며 파이프라인 출력 전달 및 전체 테스트가 통과한다.
## YOLO 추론 통계 및 출력 통일

### 사용자 시나리오

사용자가 단일 추론 Step 또는 배치 추론 Step을 선택해도 `StreamReport`는 같은 항목 이름으로 완료된 추론 요청 수와 요청당 평균 시간을 표시한다.

### 요구사항

- **FR-036**: `YoloDetect`와 `YoloDetectBatch`는 동일한 추론 건수 및 시간 통계 항목에 기록해야 한다.
- **FR-037**: 추론 요청을 시작하지 못한 입력은 추론 건수에 포함하지 않아야 한다.
- **FR-038**: `StreamReport`는 두 Step에 대해 동일한 `추론 {평균 시간}ms ({건수}건)` 형식을 사용해야 한다.

### 성공 기준

- **SC-012**: 두 Step의 완료된 요청 두 건은 각각 추론 2건으로 표시되고 같은 보고 문구를 사용한다.
## 단일 YOLO 추론 간격

### 사용자 시나리오

사용자가 `YoloDetect`에 추론 간격을 지정하면 첫 프레임과 지정된 간격의 프레임만 추론하고 나머지 프레임은 원본 그대로 전달한다. 현재 01·02 예제는 모두 `YoloDetectBatch`를 사용한다.

### 요구사항

- **FR-039**: `YoloDetect`는 1 이상의 정수 `inference_interval`을 지원하고 기본값은 1이어야 한다.
- **FR-040**: 첫 프레임을 포함해 설정된 간격의 프레임만 추론하며 건너뛴 프레임은 `detections=None`으로 순서대로 전달해야 한다.
- **FR-041**: 추론에 실패한 프레임이 있어도 다음 선택 프레임의 위치는 바뀌지 않아야 한다.
- **FR-042**: `YoloDetect`를 등록한 파이프라인은 클래스명과 같은 YAML 섹션의 `inference_interval` 값을 적용해야 한다. 현재 예제의 배치 설정은 `YoloDetectBatch`에만 적용한다.

### 성공 기준

- **SC-013**: 간격 3에서 7개 입력 중 1, 4, 7번째 프레임만 추론하고 출력 프레임 7개를 모두 전달한다.
## 프레임 보고 상세 출력 고정 및 단일 YOLO 설정 확인

### 사용자 시나리오

사용자는 `StreamReport`의 별도 상세 출력 설정 없이 항상 FPS, 프레임 처리 시간, 추론 통계와 측정된 단계별 지연을 줄 단위로 확인한다. 현재 01·02 예제는 모두 공유 설정의 배치 YOLO 옵션을 사용한다.

### 요구사항

- **FR-043**: `StreamReport`는 `details` 설정 없이 항상 상세 보고 형식으로 출력해야 한다.
- **FR-044**: 예제 설정에는 더 이상 `StreamReport.details`가 없어야 한다.
- **FR-045**: `YoloDetect`는 등록 시 받은 `classes`, `confidence`, `gpu_id`를 추론 요청에 전달해야 한다. 01·02 예제는 `YoloDetectBatch` 설정을 사용한다.

### 성공 기준

- **SC-014**: 기본 `StreamReport`가 두 줄 상세 보고를 출력하며 `YoloDetect`를 등록한 경우 해당 단계의 설정 값이 실제 추론 호출에 사용된다.
## 배치 추론 지연 최소화 경로 고정

### 사용자 시나리오

사용자는 별도의 지연 모드 설정 없이 `YoloDetectBatch`를 사용한다. 선택 프레임의 추론 결과를 받은 다음에 다음 입력을 읽으며, 불필요한 입력 선행 읽기와 프레임 보관을 하지 않는다.

### 요구사항

- **FR-046**: `YoloDetectBatch`는 기존 지연 최소화 경로만 사용해야 한다.
- **FR-047**: `low_latency` 설정은 제거하고 이전 설정 파일에 키가 남아 있으면 명확한 오류를 내야 한다.
- **FR-048**: 추론 간격, 프레임 순서, GPU 이벤트 기반 준비 순서, 오류 시 원본 전달과 추론 통계는 유지해야 한다.

### 성공 기준

- **SC-015**: 입력 선행 읽기 없이 선택 프레임마다 결과를 기다리고 모든 프레임을 순서대로 전달한다.
## 단일 스트림 감지 상자 오버레이

### 사용자 시나리오

01 예제 사용자는 감지된 물체의 사각형이 송출 영상에 표시되는 것을 본다. 추론 간격 때문에 감지 결과가 없는 프레임에도 이전 상자를 유지할 수 있다.

### 요구사항

- **FR-049**: 01 예제는 `BoxOverlay`를 감지 뒤, 인코딩 앞에 실행해 `input.detections`의 사각형을 `input.frame`에 그려야 한다.
- **FR-050**: `line_width`, `line_color`, `keep_previous` 설정을 받아 선 두께, 색상과 이전 상자 유지 여부에 적용해야 한다.
- **FR-051**: 감지 결과가 `None`이면 `keep_previous`가 참일 때만 이전 상자를 재사용하고, 물체가 없는 새 감지 결과는 이전 상자를 지워야 한다.
- **FR-052**: GPU NV12 프레임 전체를 CPU로 복사하지 않고 원본 프레임에 표시해야 한다.
- **FR-053**: 지원하지 않는 픽셀 형식과 잘못된 색상, 두께, 유지 설정은 명확한 오류로 알려야 한다.

### 성공 기준

- **SC-016**: GPU NV12 프레임에서 지정한 녹색 두께 2의 사각형이 인코딩 전에 나타나며 감지 결과 없음, 빈 결과, 좌표 경계와 이전 상자 유지 동작을 검증한다.

## 배치 검출 좌표의 GPU 완료 보장

### 사용자 시나리오

사용자가 배치 추론 뒤에 사각형을 그릴 때, 검출된 자동차의 위치에만 정상적인 사각형이 표시된다. GPU 작업 완료 시점에 따라 사각형이 다른 곳에 나타나거나 길게 늘어나지 않는다.

### 요구사항

- **FR-054**: 배치 추론은 검출 좌표의 GPU 후처리가 끝나기 전에 결과를 소비하는 단계가 좌표를 읽지 못하게 해야 한다.
- **FR-055**: 배치 요청이 여러 개여도 각 요청의 검출 결과와 완료 상태가 해당 프레임에 정확히 대응해야 한다.

### 성공 기준

- **SC-017**: 지연된 GPU 좌표 계산을 포함한 테스트에서 소비자가 항상 완료된 좌표를 읽으며, 배치 요청마다 올바른 결과를 받는다.

### 명확화 결과

- 오류가 보고된 01 예제의 배치 추론 결과 전달 경로를 수정 범위로 정한다. 기존 사각형 유지 옵션은 사용자가 명시한 동작이므로 유지한다.
## 프레임 통계 모듈 이름 정리

### 사용자 시나리오

개발자는 프레임 통계 구현을 역할이 드러나는 모듈 이름에서 찾고, 기존 `StreamReport` 사용 방식으로 통계를 확인한다.

### 요구사항

- **FR-056**: 프레임 통계 구현 파일은 `stream_report.py`라는 이름을 사용해야 한다.
- **FR-057**: 통계 기록을 사용하는 모든 단계와 테스트는 새 모듈을 참조하고 기존 통계 동작을 유지해야 한다.

### 성공 기준

- **SC-018**: 기존 공개 `StreamReport` 가져오기가 동작하며, 이전 모듈 경로를 참조하는 실행 코드가 없다.

### 명확화 결과

- 요청은 파일명 변경이며 공개 클래스명과 동작은 유지한다. 기존 모듈 경로에 대한 호환성 유지 요구는 없다.
## 여러 RTSP 스트림의 동시 실행

### 사용자 시나리오

사용자는 02 다중 스트림 예제를 실행하여 현재 설정된 다섯 영상의 파이프라인을 한 번에 시작한다. 한 영상이 계속 재생되어도 나머지 영상의 시작이 막히지 않는다.

### 요구사항

- **FR-058**: 02 다중 스트림 예제는 각 파이프라인의 실행을 별도 스레드에서 시작해야 한다.
- **FR-059**: 예제 프로세스는 시작한 모든 파이프라인의 종료를 기다리고 실행 오류를 호출자에게 전달해야 한다.
- **FR-060**: 각 파이프라인은 영상별로 구별되는 이름과 송출 주소를 사용해야 한다.

### 성공 기준

- **SC-019**: 예제에 지정된 모든 파이프라인의 실행이 첫 파이프라인 종료 전에 시작되며, 완료 또는 실패가 호출자에게 반영된다.

### 명확화 결과

- 사용자 요청의 스레드는 예제 호출자 프로세스의 실행 스레드를 뜻한다. 기존 중앙 프로세스 실행 및 모델 배치 공유 방식은 유지한다.
