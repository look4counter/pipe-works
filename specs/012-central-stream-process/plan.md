# 구현 계획: 중앙 스트림 프로세스

**날짜**: 2026-10-03  
**명세**: [spec.md](spec.md)

## 요약

`Pipeline.run()`은 중앙 프로세스에 파이프라인 실행을 요청하고 결과를 기다린다. 중앙 프로세스는 요청마다 실행 스레드를 만들되 영상과 GPU 객체를 프로세스 밖으로 보내지 않는다. 클라이언트 연결 종료는 해당 실행의 중단 신호가 된다.

## 기술 맥락

- 언어: Python 3.11.9
- 플랫폼: Windows, CUDA
- 통신: 로컬 이름 있는 파이프
- 전달: `cloudpickle`로 사용자 정의 단계가 포함된 파이프라인 직렬화
- 검증: 기존 `unittest` 및 프로세스 통합 테스트
- 규모: 약 50개 동시 영상 스트림을 설계 대상으로 두되 처리량은 GPU 및 영상 규격에 따라 측정

## 구성

- `src/pipeworks/main.py`: 중앙 프로세스 시작, 중복 시작 방지, 요청 수신, 스트림 실행 및 취소
- `src/pipeworks/pipeline.py`: 원격 `run()`과 내부 실행 경로 구분
- `src/pipeworks/local_yolo.py`: 중앙 프로세스 내부 모델별 배치 실행
- `src/pipeworks/embedded/yolo_detect_batch.py`: 내부 배치 실행 호출
- `tests/`: 요청·취소·동시성·오류 검증

## 주요 결정

1. 첫 `run()` 호출이 중앙 프로세스를 자동 시작한다. 이미 실행 중이면 연결한다.
2. 요청 데이터에는 GPU 프레임이 포함되지 않는다. 파이프라인 구성만 전송한다.
3. 중앙 프로세스는 모델별 배치 큐를 공유한다.
4. 클라이언트 연결이 끊기면 해당 스트림의 중단 이벤트를 설정한다. 실제 작업은 영상 입출력 시간 제한과 단계의 협조적 중단에 따른다.
5. 중앙 프로세스가 죽으면 `run()`은 연결 실패를 예외로 전달한다.
6. 로컬 파이프 주소는 Windows 사용자 SID를 포함해 계정 간 충돌을 막는다. 시작 실패 시 자식 프로세스의 오류 출력을 호출자에게 전달한다.

## 헌장 확인

현재 헌장 파일은 예시 자리표시자만 포함한다. 실행 가능한 추가 제약은 없다.
# 호출자 콘솔 출력 구현 계획

## 기술 맥락

- 중앙 프로세스는 Windows 이름 있는 파이프로 각 호출자와 통신한다.
- 파이프라인은 서로 다른 스레드에서 동시에 실행된다.
- 중앙 프로세스의 표준 출력은 버려지므로 호출자 연결로 출력을 전달한다.

## 설계

1. 중앙 프로세스에 스레드별 출력 대상을 구분하는 표준 출력 프록시를 설치한다. 출력 대상이 없는 스레드는 기존 표준 출력으로 보낸다.
2. 파이프라인 실행 스레드가 출력한 문자열을 해당 연결의 출력 메시지로 전송한다. 연결의 모든 송신은 잠금으로 직렬화한다.
3. 호출자는 출력 메시지를 받는 즉시 자신의 현재 표준 출력에 쓰고, 완료 메시지까지 기다린다.
4. 연결이 끊기면 기존 중단 신호를 사용하고 출력 송신 실패가 다른 파이프라인을 중단시키지 않게 한다.

## 검증

- 서로 다른 호출자 두 곳에서 출력이 격리되는 통합 테스트를 실행한다.
- 기존 중앙 프로세스의 정상 완료, 실패, 호출 종료 테스트를 실행한다.

## Sink 출력 전달 보완 계획

`Sink` 작업 스레드를 시작할 때 파이프라인 실행 스레드의 출력 대상을 캡처한다. 작업 스레드에서 그 대상만 활성화하고 종료 시 해제한다. 기존 연결 송신 잠금이 `StreamReport`와 `Sink`의 동시 출력을 직렬화한다. 두 호출자의 `Sink` 출력을 비교하는 통합 테스트로 격리를 확인한다.

## GPU 큐 동기화 보완 계획

NV12 복제 명령 뒤 원본 CUDA 스트림에 이벤트를 기록해 내부 추론 요청에 함께 싣는다. 모델별 작업자 스레드는 요청을 GPU에서 읽기 전에 자신의 CUDA 스트림이 그 이벤트를 기다리게 한다. 호스트 `synchronize()`를 제거하고 실제 GPU 추론, 프레임 순서, 동시 배치 및 지연 추론 테스트를 실행한다.

## 프레임 지연 진단 계획

`YoloDetectBatch`에서 프레임을 읽은 시점과 내보낸 시점을 기록하고, `NvidiaEncode`의 인코딩 호출 및 `RTSPPublish`의 송출 호출 시간을 집계한다. `StreamReport`는 단계별 수치를 항상 상세 형식으로 표시한다. 지연을 넣은 테스트로 각 단계 집계를 확인한다.

## 단일 영상 지연 최소화 계획

파이프라인 스레드가 입력을 한 장씩 읽고 선택 프레임만 중앙 프로세스의 모델별 큐에 제출해 결과를 기다린다. 새 입력을 미리 읽지 않으므로 프레임 처리 시간에 앞 프레임의 후속 처리 대기가 섞이지 않는다. GPU 이벤트로 복제본의 준비 순서를 보장한다.

## 헌장 확인

프로젝트 헌장은 미작성 템플릿이므로 추가 제약이 없다.
# GPU 내부 배치 추론 계획

## 기술 맥락과 조사

- 현재 `local_yolo.py`는 중앙 프로세스 안에서 모델별 큐를 소유하고 NV12를 GPU RGB 텐서로 변환한다.
- 설치된 Ultralytics의 텐서 입력은 정규화된 BCHW RGB와 32 배수 크기를 요구하며 기본 감지 후처리는 원본 영상을 CPU 배열로 만든다.
- 중앙 프로세스가 모델을 소유하므로 프로세스 간 GPU IPC보다 같은 프로세스의 텐서를 직접 큐로 전달하는 것이 적합하다.

## 설계

1. 배치 요청과 설정 읽기, 옵션별 묶기 기능을 `local_yolo.py`에 둔다.
2. GPU NV12를 RGB 텐서로 바꾸고 원본 비율을 유지한 채 모델 입력 크기로 조정한다.
3. GPU 텐서를 받는 감지 후처리를 사용하여 기본 CPU 원본 영상 변환을 피하고, 결과 좌표를 원본 영상 크기로 돌린다.
4. 별도 YOLO 작업자 프로세스 없이 중앙 프로세스 통합 테스트로 검증한다.

## 검증

- 실제 `.pt` 및 `.engine` 추론과 모델별 동시 배치, GPU 결과, 원본 좌표 크기를 확인한다.
- 감지 Step과 중앙 프로세스 및 전체 테스트를 실행한다.
## 실행별 통계 분리 계획

각 `Pipeline._run_local` 실행에 고유한 통계 수집기를 생성한다. `stream_report` 함수는 현재 실행 문맥에 연결된 수집기에 기록하고 `StreamReport`는 같은 수집기의 구간 통계를 읽는다. `YoloDetectBatch`의 추론 시간은 결과를 기다리는 파이프라인 스레드에서 기록한다. 별도 모델 작업 스레드는 보고 수집기를 직접 갱신하지 않는다. 독립 Step 호출은 기본 수집기를 사용한다. 서로 겹치는 실행의 통계 분리를 검증한다.

중앙 프로세스의 실행 코드가 변경되므로 통신 프로토콜 식별자를 갱신해 기존 상주 프로세스에 새 실행 요청이 전달되지 않도록 한다.
## 중앙 프로세스 유휴 종료 계획

서버 수락 루프에서 실제 파이프라인 요청을 읽은 뒤 활성 연결 수를 증가시킨다. 연결 처리 종료 시 감소시키고 0이면 유예 타이머를 예약한다. 타이머는 전용 종료 확인 메시지로 막힌 수락 루프를 깨우며, 수락 루프는 여전히 활성 연결이 0인지 확인하고 리스너를 닫는다. 새 요청이 들어오면 타이머를 취소한다. 시작 시에도 같은 유예 타이머를 예약해 요청 없이 시작한 서버가 남지 않도록 한다. 시작 확인용 요청은 연결 수에 포함하지 않는다.
## 중앙 프로세스 콘솔창 숨김 계획

`_start_server`는 현재 Python 실행 파일과 같은 디렉터리의 `pythonw.exe`가 있으면 이를 우선 사용한다. 없으면 `python.exe`를 `CREATE_NO_WINDOW`로 시작한다. 두 경로 모두 표준 오류 파이프, 표준 출력과 입력의 무효화, 독립 프로세스 그룹을 유지한다. `DETACHED_PROCESS`는 `CREATE_NO_WINDOW`를 무효화하므로 제거한다. 프로토콜 식별자를 갱신해 기존 상주 서버와 구별한다. 실제 서버에서 콘솔 핸들 부재와 Step 출력 전달을 검증한다.
## YOLO 추론 통계 및 출력 통일 계획

`YoloDetect`의 측정 시작점을 입력 변환 뒤의 추론 요청 직전으로 이동하고, 모델 준비와 예측 및 결과 반환을 마칠 때 공통 `record_inference`에 기록한다. 배치 경로의 기존 `record_inference` 측정은 유지한다. 보고 수집기에서 단일 추론 전용 카운터와 출력 분기를 제거하고 공통 건수 및 평균만 반환한다. 입력 검증 실패와 추론 실패의 건수 처리, 두 모드의 보고 문구를 테스트한다. 중앙 프로세스 식별자를 갱신해 실행 중인 구버전 서버와 구분한다.
## 단일 YOLO 추론 간격 계획

`YoloDetect.configure`는 기본값 1의 간격 설정과 양의 정수 검증을 적용한다. `process`는 입력 순번을 세고 선택되지 않은 프레임의 감지 결과를 비운 뒤 즉시 전달한다. 실패한 프레임도 순번에 포함한다. 현재 01·02 예제는 모두 `YoloDetectBatch`를 사용하며 공유 YAML의 `YoloDetectBatch` 섹션을 읽는다. `YoloDetect`의 설정 전달은 별도 단계 등록 테스트로 검증한다.
## 프레임 보고 상세 출력 고정 및 단일 YOLO 설정 확인 계획

`StreamReport`는 `details` 설정 없이 단계별 지연을 항상 출력한다. 공유 YAML에 `StreamReport` 섹션은 없다. `YoloDetect`는 등록 시 받은 `classes`, `confidence`, `gpu_id`를 `model.predict`에 전달한다. 현재 공유 예제 YAML에는 `YoloDetectBatch` 설정만 있다.
## 배치 추론 단일 경로 계획

`YoloDetectBatch.process`에 지연 최소화 경로를 직접 두고 입력 선행 읽기 스레드, 보류 큐, 비동기 추론 작업과 모드 분기를 삭제한다. `low_latency` 구성 항목은 삭제하고 남아 있는 이전 구성에는 오류를 반환한다. 기존 추론 간격과 오류 복구, CPU 호스트 동기화 없는 GPU 복제, 단계별 통계를 검증한다. 공유 예제 구성과 안내 문서를 수정하고 중앙 프로세스 식별자를 갱신한다.
## 단일 스트림 감지 상자 오버레이 계획

01 예제의 `BoxOverlay`를 감지와 인코딩 사이에 연결하고 공유 YAML에 `line_width: 2`, `line_color: "#00ff00"`, `keep_previous: true`를 둔다. 상자 좌표만 CPU에서 읽어 화면 경계로 제한하고 프레임은 CUDA 스트림의 NV12 Y·UV 평면에 직접 쓴다. 색상은 RGB 16진수에서 NV12의 제한 범위 YUV 값으로 변환한다. 이전 상자는 좌표만 저장해 지난 프레임 GPU 메모리를 붙잡지 않는다. 감지 결과가 없는 프레임과 빈 감지 결과를 구분한다. 설정 검증, 경계 좌표, 색상·두께, 이전 상자 유지 및 실제 01 예제 연결을 테스트한다. 중앙 프로세스 식별자를 갱신한다.

## 배치 검출 좌표 완료 보장 계획

local_yolo.py의 모델 작업 스레드가 결과 좌표 복원 작업을 GPU에 기록한 뒤 CUDA 이벤트를 기록한다. 요청을 기다리던 파이프라인 스레드는 해당 이벤트의 완료를 확인한 후 결과를 반환한다. 이로써 BoxOverlay가 좌표를 CPU로 읽을 때 최신 값을 받는다. 각 요청은 자신의 결과와 완료 이벤트를 같은 작업에서 받는다. 	ests/test_local_yolo.py에 지연된 GPU 연산을 이용한 회귀 테스트를 추가하고 전체 테스트를 실행한다. 전송 대상은 작은 좌표만이며 원본 프레임의 CPU 복사는 추가하지 않는다.
## 프레임 통계 모듈 이름 변경 계획

`src/pipeworks/embedded/report.py`를 같은 디렉터리의 `stream_report.py`로 옮긴다. 파이프라인과 통계를 기록하는 단계의 직접 import를 새 경로로 변경한다. 테스트의 모듈 import도 새 경로로 맞춘다. 공개 `StreamReport` 재수출과 통계 수집 방식은 유지하며 전체 테스트로 회귀를 확인한다.
## 다중 RTSP 예제 동시 실행 계획

02 예제는 현재 다섯 영상의 목록과 파이프라인 구성을 사용한다. 파이프라인 이름에 영상 식별자를 포함하고, `ThreadPoolExecutor`에서 각 `Pipeline.run()`을 제출한다. 모든 작업을 제출한 뒤 각 결과를 확인하여 호출자가 작업 완료를 기다리고 예외를 받도록 한다. 실제 RTSP 서버 연결 없이 예제의 구성과 실행 순서를 검증한다.
