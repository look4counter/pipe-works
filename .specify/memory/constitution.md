# Pipe Works 헌법

## 핵심 원칙

### I. 한국어 명세 우선

모든 Spec Kit 명세 산출물(예: `spec.md`, `plan.md`, `tasks.md`, 체크리스트 및 사용자 대상
수용 기준)은 반드시 한글로 작성한다. 코드 식별자, 명령어, 파일 경로, 프로토콜 필드명 및
외부 라이브러리의 고유 명칭은 정확성을 위해 원문을 유지할 수 있다. 번역이 필요한 기술
용어는 최초 사용 시 한글 설명과 원어를 함께 제공한다.

근거: 프로젝트의 요구사항과 검토 결과를 팀이 오해 없이 공유하고 추적 가능하게 만든다.

### II. 파이프라인 계약 보존

인코드, 디코드, 송신, 수신 및 지휘(conductor) 계층 간의 입력·출력 형식, 오류 처리, 자원
소유권 및 하드웨어 가속 선택 규칙은 명시적 계약으로 취급한다. 계약을 변경하는 작업은
호환성 영향, 이전 경로 및 검증 방법을 명세에 반드시 기록해야 한다.

근거: 비디오 파이프라인의 계층 간 불일치는 실행 시점의 데이터 손상이나 실패로 이어질 수 있다.

### III. 검증 가능한 변경

동작을 변경하거나 추가하는 모든 작업에는 재현 가능한 검증 기준이 있어야 한다. 단위
테스트는 변환·오류 처리·선택 로직을 다루며, 결함 수정에는 회귀 검증을 포함한다. 테스트가
현실적으로 불가능한 하드웨어 의존 경로는 그 사유와 수동 검증 절차를 기록한다.

근거: CPU 및 NVIDIA 경로의 동등성과 회귀 방지는 추측이 아닌 증거로 판단해야 한다.

### IV. 통합 경로 검증

새로운 또는 변경된 데이터 경로는 실제 경계(파일·스트림·HTTP 또는 CLI)를 통과하는 통합
검증을 수행해야 한다. CPU와 NVIDIA 구현이 같은 기능을 제공하는 경우, 지원 환경에서 결과와
실패 동작의 일관성을 확인한다.

근거: 개별 모듈이 정상이어도 코덱, 프레임, 네트워크 경계에서 통합 실패가 발생할 수 있다.

### V. 단순성 및 관찰 가능성

구현은 현재 요구사항에 필요한 가장 단순한 구조를 우선한다. 운영 또는 디버깅이 필요한
경로는 원인 분석에 충분한 구조화된 로그와 오류 문맥을 제공해야 하며, 비밀값이나 원본 영상
데이터를 로그에 노출해서는 안 된다.

근거: 성능 민감한 파이프라인에서는 불필요한 복잡성과 관찰 불가능성이 유지보수 비용을 키운다.

## 기술 및 문서 제약

프로젝트는 Python 3.11.9를 사용한다. 의존성 변경은 `pyproject.toml` 및 잠금 파일에
일관되게 반영하고, CPU 전용 환경과 NVIDIA 가속 환경에서의 영향 범위를 문서화한다. 명세
문서는 Markdown으로 작성하며, 모든 요구사항은 검증 가능한 수용 기준을 포함해야 한다.

## 개발 워크플로

기능 작업은 한글 명세, 구현 계획, 의존 순서의 작업 목록 순으로 구체화한다. 구현 전후에
해당 테스트를 실행하고 결과를 검토한다. 코드 검토자는 본 헌법 준수, 계약 변경의 문서화,
테스트 또는 수동 검증 증거를 확인해야 한다. 명세와 구현의 불일치는 구현을 기준으로 숨기지
말고, 명세를 수정하거나 호환성 결정을 기록해 해소한다.

## 거버넌스

본 헌법은 프로젝트의 다른 개발 관행과 충돌할 때 우선한다. 개정은 변경 사유, 영향을 받는
원칙 및 필요한 마이그레이션을 문서화한 뒤 검토를 거쳐 반영한다. 원칙의 추가 또는 실질적
확장은 MINOR, 호환되지 않는 원칙의 제거·재정의는 MAJOR, 의미를 바꾸지 않는 명확화는 PATCH
버전을 올린다. 모든 코드 검토와 명세 검토는 본 헌법 준수를 확인해야 한다.
