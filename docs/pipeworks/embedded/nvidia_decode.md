# NvidiaDecode: 하드웨어 비디오 디코딩

NVIDIA GPU를 사용해 RTSP 패킷을 디코딩합니다. 내부 스레드에서 수신·디코딩을 계속 수행하며, 대기 프레임을 최대 30개 보관하며 초과 시 가장 오래된 대기 프레임을 버립니다. 별도의 최신 프레임 Step이 필요하지 않습니다.

**파일 위치:** `src/pipeworks/embedded/nvidia_decode.py`  
**역할**: Processing Step (디코딩)

---

## 📚 개요

- NVIDIA GPU 하드웨어 가속 디코딩
- CPU 사용률 감소
- RTSPSource 다음에 배치 (선택사항)

---

## 🔑 사용법

```python
from pipeworks import Backend
from step.yolo_pre_process import YoloPreProcess
from step.yolo_post_process import YoloPostProcess

from pathlib import Path
from pipeworks import Pipeline
from pipeworks.embedded import RTSPSource, NvidiaDecode, YoloInference

pipeline = Pipeline("gpu-decode", config=Path("config.yaml"))
pipeline.step(RTSPSource(url="rtsp://camera"))
pipeline.step(NvidiaDecode())  # GPU 디코딩
pipeline.step(YoloPreProcess()).step(YoloInference(model_path=Path("models/yolov8n.pt"), backend=Backend.ULTRALYTICS)).step(YoloPostProcess())
pipeline.run()
```

---

## ⚙️ 설정 (config.yaml)

```yaml
NvidiaDecode:
  gpu_id: 0                  # 사용할 GPU 번호 (기본값 0)
```

## 프레임 전달과 메모리

대기 큐는 30개입니다. 소비는 FIFO 순서이며 큐가 가득 차면 가장 오래된 대기 프레임을 제거하고 새 프레임을 추가합니다. 소비 중인 프레임은 제거하지 않습니다. 여러 디코딩 출력과 EOF 출력도 순서대로 게시합니다. 따라서 모든 프레임을 보존해야 하는 녹화 용도에는 적합하지 않습니다.

압축 패킷은 순서대로 디코딩합니다. PyAV 패킷의 원본 버퍼 주소와 크기를 직접 전달하여 Python 바이트 및 ctypes 중간 버퍼 복사를 하지 않습니다. 디코더 호출이 반환될 때까지 패킷 객체를 유지합니다. RTSPSource에서 RTSPPublish로 직접 전달하는 패킷 계약도 유지됩니다. 디코딩 자체가 입력 속도보다 느리거나 수신 이전에 지연이 생긴 경우에는 이 슬롯만으로 지연을 제거할 수 없습니다.

`GetLockedFrame()`으로 디코더 출력 버퍼를 잠그고 같은 GPU 주소의 CUDA `torch.Tensor`를 전달합니다. 이 단계에서는 영상 데이터를 복사하거나 별도 영상 버퍼를 할당하지 않습니다. `Decode()` 결과를 단순히 보관하는 방식은 출력 풀의 재사용을 막지 못하므로 사용하지 않습니다. 텐서는 DLPack으로 재공유할 수 있습니다.

별도 소비 CUDA 스트림이 준비 이벤트를 기다립니다. 후속 처리 뒤 완료 이벤트를 기록하고, 마지막 텐서 참조가 해제되고 GPU 이벤트가 끝난 버퍼만 `UnlockFrame()`으로 반환합니다. 일반 전달 경로에서 CPU가 스트림 전체를 동기화하지 않습니다. 종료 시에는 안전하게 남은 이벤트를 기다립니다.

대기 큐는 최대 30개이며, 소비 중·비동기 소비자 보관·반환 대기를 합친 잠금 출력 버퍼 상한은 34개입니다. 상한에 도달하면 버퍼 반환을 기다립니다. 외부 코드에서 출력을 계속 보관하면 생산이 멈출 수 있으므로 사용한 프레임 참조를 해제해야 합니다. 디코더 내부 참조·재정렬 버퍼 수는 별도입니다.

CudaAsync는 GPU 작업 완료 후 내부 작업 컨텍스트의 원본 프레임 참조를 정리하며, 출력 컨텍스트와 외부에서 보관한 텐서는 유지합니다. 감싸진 Step은 처리에 필요한 프레임을 yield 전에 사용해야 하며, 이후까지 보관하려면 텐서 참조를 별도로 유지해야 합니다. 완료 요청의 생성기 지역 변수 때문에 잠금 버퍼가 소진되는 경우는 내부에서 정리합니다.

설치된 PyNvVideoCodec 2.2.2의 잠금 API를 사용하며, EOF는 길이 0인 패킷으로 지연 프레임을 회수합니다. 공유 레이아웃은 NV12, P016, NV16, P216, YUV444, YUV444_16BIT를 지원하고 크기·행 간격을 검증합니다.

기존 `frame`, `video_stream`, `cuda_stream`, `pixel_format` 속성과 다음 진단 속성을 제공합니다.

| 속성 | 의미 |
|---|---|
| `decoded_at` | 디코딩 출력 게시 시점의 `time.perf_counter()` 값 (GPU 완료 시각은 아님) |
| `processing_started_at` | 후속 단계에 전달하는 시점의 같은 시계 값 |
| `decode_dropped_frames` | 이번 입력 구간에서 소비 전에 교체하거나 건너뛴 프레임의 누적 개수 |

두 시각의 차이는 디코딩 이후 슬롯 대기 시간입니다. 카메라 촬영 시점부터의 지연을 나타내지는 않습니다.

## 오류와 종료

디코더 네이티브 호출에서 복구 가능한 오류가 발생하면 전체 파이프라인을 종료하지 않고 자동 복구합니다. 오류 패킷과 대기 프레임을 버리고 다음 키프레임에서 새 디코더를 생성합니다. 재생성이나 디코딩이 다시 실패하면 다음 키프레임에서 계속 재시도합니다. 오류 원인은 경고 로그로, 실제 프레임 출력 재개는 정보 로그로 기록합니다. 별도 설정은 필요하지 않습니다.

RTSP 재연결 등으로 입력 video_stream 객체가 교체되어도 기존 디코더와 대기 큐를 초기화하고 새 스트림의 키프레임부터 처리합니다. 이미 후속 단계에 전달한 텐서와 DLPack 별칭은 마지막 참조와 GPU 작업이 끝날 때까지 기존 디코더의 잠금을 유지합니다. 소비자 CUDA 스트림은 복구 전후에 동일하게 유지합니다.

복구·입력 교체·생산자 종료 시 디코딩 스트림의 작업 완료를 기다린 뒤 기존 세대를 정리합니다. 출력 버퍼 풀이 생성되기 전 오류에도 같은 순서를 적용합니다. 정상 프레임마다 CPU 동기화는 하지 않습니다. 복구용 내부 예외는 원인 문자열만 보유하며 이전 호출의 traceback을 연결하지 않습니다. 외부 프레임이 남아 있는 풀은 디코더와 스트림을 계속 함께 보유합니다. GPU 동기화 실패는 복구 성공으로 숨기지 않고 전달합니다.

복구 중에는 출력이 잠시 멈추거나 프레임이 누락될 수 있습니다. 재개 시간은 카메라의 키프레임 및 필요한 헤더 전송 주기에 따라 달라집니다. 키프레임이 오지 않으면 입력을 계속 소비하며 기다리고 종료 요청에는 응답합니다. 마지막 지연 프레임 처리 중 디코더 오류가 발생하면 해당 출력을 버리고 정상 종료합니다. 정상 입력 종료 시에는 지연 프레임에도 FIFO 큐 정책을 적용합니다.

입력 소스 자체의 오류, 실행 전 설정 오류와 후속 처리 오류는 전달합니다. 지원하지 않는 코덱·기능과 일반 디코딩 오류는 해당 입력을 폐기하고 복구합니다. 운영체제 수준의 네이티브 충돌이나 복구 불가능한 GPU 장애까지 자동 복구를 보장하지는 않습니다. 종료나 핫스왑 시 대기 프레임을 해제하고 작업 스레드가 끝날 때까지 기다립니다.

`RTSPSource`의 재연결 대기는 취소할 수 있습니다. 이미 진행 중인 수신 호출은 기존 수신 타임아웃 또는 다음 패킷을 기다려야 하므로 유한한 수신 타임아웃을 설정해야 합니다. 사용자 정의 입력도 블로킹 읽기가 반환되거나 수신 취소 신호에 협조해야 정상적으로 종료할 수 있습니다.

## 공개 생성자와 입출력 계약

`NvidiaDecode(*, gpu_id=0)`를 사용합니다. gpu_id는 생성자와 NvidiaDecode YAML 섹션에서 지정하며 YAML 삭제 시 최초 생성자 값으로 돌아갑니다. configure 자체에는 GPU 번호의 별도 범위 검증이 없습니다. GPU 스트림 생성 오류와 실행 전 설정 오류는 전달하며, 복구 가능한 네이티브 디코더 초기화 오류는 다음 키프레임에서 다시 시도합니다.

필수 입력은 packet과 video_stream입니다. 현재 코덱 매핑은 h264와 hevc/h265입니다. 첫 입력에서 디코더와 스트림을 만듭니다. 이후 video_stream 객체 교체를 감지하면 디코더를 재생성합니다. 자동 복구 및 스트림 교체 후 재개에는 packet.is_keyframe 값이 필요하며, 이 값이 없는 입력은 키프레임으로 간주하지 않습니다.

출력은 새 PipelineContext이며 frame·video_stream·cuda_stream·pixel_format·decoded_at·processing_started_at·decode_dropped_frames를 제공합니다. 입력 packet이나 사용자 속성을 그대로 복사하지 않습니다. 패킷 하나에서 출력 프레임이 없거나 여러 개일 수 있습니다. pixel_format은 디코더의 실제 NATIVE 출력 형식이며 NV12로 고정하지 않습니다. 잠금 API 경로의 _decode_buffer는 내부 수명 관리용입니다.

## 비디오 메타데이터

video_stream은 불변 VideoStreamInfo이며 입력 연결에서 받은 같은 객체를 출력 프레임에 공유합니다. 같은 설정으로 재연결해도 새로운 메타데이터 객체가 생성되어 기존 스트림 교체 감지가 유지됩니다. codec_context.width·height와 codec.name 접근은 네이티브 리소스를 읽지 않습니다.

## 정리 중 오류

버퍼 반환에 성공하면 즉시 반환 대기 목록에서 제거합니다. 이후 다른 버퍼나 완료 이벤트가 실패해도 성공한 버퍼를 다시 반환하지 않습니다. 반환·완료 이벤트 확인에 실패한 풀은 새 프레임에 재사용하지 않으며 종료 정리와 마지막 외부 참조 반환에서도 네이티브 정리를 재시도하지 않습니다.

GPU 동기화나 정리 자체의 오류는 자동 디코더 복구로 숨기지 않고 최초 정리 오류를 전달합니다. 실패한 정리를 최종 종료에서 다시 호출해 오류를 바꾸지 않습니다. 정상 경로의 완료 이벤트 대기와 외부 텐서·DLPack 별칭의 소유자 수명은 유지합니다. 치명적 GPU 장애 이후 정상 처리를 보장하거나 GPU 컨텍스트를 자동 초기화하지 않습니다.

## 일반 실행 오류 복구

잘못된 입력·미지원 코덱·픽셀 형식·출력 레이아웃과 일반 코덱 실패는 경고를 기록하고 해당 입력을 버린 뒤 디코더를 재생성합니다. 다음 키프레임에서 재개합니다. 실행 전 설정 검증과 상류 사용자 생성기 자체의 오류, 명시적인 GPU 장애·버퍼 안전성·동기화 실패는 전파합니다.
